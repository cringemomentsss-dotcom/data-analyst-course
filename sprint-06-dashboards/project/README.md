# Проект спринта 6. Дашборд сервиса доставки «Скороход»

## Что это за задание

Проект с ревью. В прошлом спринте ТЗ было исчерпывающим, и задача сводилась к точному исполнению. Здесь **ТЗ намеренно неполное**.

Заказчик перечислил не всё, что ему нужно, — как это обычно и бывает. Часть требований придётся восстановить из описания бизнеса и здравого смысла. Восстановленные требования нужно **выписать отдельным списком и обосновать**: «я добавил это, потому что из описания следует, что…».

Это второй по важности навык аналитика после умения считать. Первый — уточнять. Второй — достраивать недосказанное так, чтобы заказчик узнал свою задачу.

## Контекст бизнеса

«Скороход» — сервис доставки еды, работает с октября 2025 в шести городах Грузии и Армении. Модель: клиент заказывает через приложение, ресторан готовит, курьер везёт. Сервис зарабатывает **комиссию с суммы заказа** — от 11 до 26 процентов в зависимости от договора с рестораном. Доставка оплачивается клиентом отдельно, скидки по промокодам сервис финансирует сам.

Сервис вырос за девять месяцев с трёх с половиной тысяч заказов в месяц до почти сорока тысяч. Рост неравномерный по городам: Тбилиси и Ереван — основные рынки, остальные четыре города поменьше.

Три вещи, которые беспокоят операционного директора:

Первое — **курьеры**. Их набирают постоянно, но они и уходят постоянно, а в выходные в некоторых городах заказов больше, чем курьеров. Сколько именно нужно и где — никто не считает, добавляют на глаз.

Второе — **отмены**. Отменяют и клиенты, и рестораны, и курьеры, причины у всех разные, и никто не смотрит, где именно теряются деньги.

Третье — **время доставки**. У сервиса обещание «45 минут», и директор уверен, что оно выполняется. Проверять никто не проверял.

Дашборд заказывает **операционный директор**. Смотреть будет он сам и руководители городов, раз в неделю на планёрке.

## Что заказчик попросил явно

> «Сделай нам дашборд по доставке. Нужно видеть:
>
> — сколько заказов и на какую сумму;
> — как это меняется по месяцам;
> — разбивку по городам;
> — сколько в среднем идёт доставка;
> — сколько заказов отменяется.
>
> Ну и чтобы можно было выбрать город и посмотреть отдельно.»

Это всё. Пять пунктов и один фильтр.

## Что с этим делать

Пять пунктов — не дашборд, а список тем. Из описания бизнеса выше следует минимум ещё пять-шесть требований, которые заказчик не назвал, но без которых дашборд не ответит на его собственные вопросы.

Подумай, прежде чем читать дальше. Подсказки по направлениям:

- Он зарабатывает комиссию, а не GMV. Спросил про «сумму», но какая сумма его интересует?
- Он назвал обещание «45 минут». Среднее время доставки на этот вопрос не отвечает.
- Он беспокоится про курьеров и выходные. Что нужно показать, чтобы он мог принять решение о найме?
- Он сказал «отмены», но отмены бывают трёх типов, и решения по ним разные.
- Он смотрит раз в неделю на планёрке. Что должно быть видно за три секунды?
- Он финансирует скидки сам. Видно ли, сколько это стоит?

Восстановленные требования выпиши в отдельный файл с обоснованием по каждому.

## Данные

Схема `delivery`. Поднять:

```bash
make delivery
```

| Таблица | Строк | Зернистость |
|---|---|---|
| `cities` | 6 | город |
| `restaurants` | 860 | ресторан |
| `couriers` | 1 100 | курьер |
| `customers` | 38 000 | клиент |
| `orders` | 150 741 | заказ |
| `order_items` | 373 900 | позиция заказа |

Период: октябрь 2025 — июнь 2026.

Что нужно знать:

- `orders.status` — `delivered`, `cancelled_by_user`, `cancelled_by_restaurant`, `cancelled_by_courier`.
- `items_total` — сумма блюд без доставки и без скидки.
- Выручка сервиса = `items_total × commission_pct / 100`. GMV = `items_total + delivery_fee − discount`.
- `restaurants.commission_pct` — индивидуальная комиссия ресторана.
- `couriers.terminated_date IS NULL` — курьер работает.
- `orders.rating` заполнен не всегда.
- В данных есть дефекты, и один из них искажает главную метрику почти вдвое.

## Требование к архитектуре

Tableau Public **не подключается к базам данных**. Значит цепочка обязательна:

```
PostgreSQL → SQL-витрина → CSV → Tableau Public
```

Витрина считается в SQL, файл запроса лежит в репозитории, выгрузка делается командой:

```bash
make export SQL=путь/к/mart.sql OUT=путь/к/mart.csv
```

Вся тяжёлая логика — соединения, очистка, определения метрик, агрегация — в SQL. Tableau только рисует и считает доли, ранги и приросты.

Витрин может быть несколько с разной зернистостью. Одна огромная витрина «на все случаи» — плохое решение.

## Эталонные числа

Для самопроверки. Все — по доставленным заказам за весь период.

| Метрика | Значение |
|---|---|
| Доставленных заказов | 138 380 |
| GMV | 7 291 061 |
| Выручка сервиса (комиссия) | 1 403 415 |
| Средний чек (GMV на заказ) | 52,69 |
| Скидок выдано | 519 880 |
| Среднее время доставки (с очисткой) | 39,3 мин |
| Медиана времени доставки | 39,2 мин |
| 90-й перцентиль времени доставки | 52,3 мин |
| Доля заказов в пределах 45 минут | 71,7% |
| Отмен всего | 8,2% (клиент 4,05%, ресторан 2,66%, курьер 1,49%) |
| Средняя оценка | 4,17 |
| Доля заказов с оценкой | 42,1% |
| Курьеров всего / работает | 1 100 / 827 |

**Если среднее время доставки получилось 58,5 минуты — данные не очищены.** Разница с настоящими 39,3 составляет 49%, и обещание «45 минут» при этом выглядит проваленным, хотя на самом деле выполняется в 72% случаев. Это ровно тот случай, когда неочищенные данные приводят к неверному управленческому решению.

Заодно обрати внимание: медиана в этих данных равна 39,2 и даёт правильный ответ **без очистки**. Полагаться на это не надо, но как сигнал «со средним что-то не так» — работает.

## Критерии приёмки

Обязательные:

- [ ] Три вопроса о пользователе (кто, какое решение, что сделает иначе) отвечены письменно до начала работы.
- [ ] Восстановленные требования выписаны отдельно, по каждому — обоснование из описания бизнеса. Минимум пять.
- [ ] Прототип от руки есть в репозитории и сделан до сборки.
- [ ] Витрина считается в SQL, файлы запросов в репозитории, выгрузка воспроизводима командой `make export`.
- [ ] Тяжёлая логика не в Tableau: определения метрик и очистка — в SQL.
- [ ] Данные очищены; среднее время доставки совпадает с эталонным.
- [ ] Все эталонные числа воспроизводятся на дашборде при снятых фильтрах.
- [ ] Обещание «45 минут» измерено долей заказов, уложившихся в срок, а не средним.
- [ ] Отмены разложены по трём типам.
- [ ] Выручка сервиса показана отдельно от GMV.
- [ ] Дашборд помещается в один экран, размер фиксированный.
- [ ] Главная метрика читается за три секунды.
- [ ] Не больше семи блоков.
- [ ] Ключевые показатели даны со сравнением с прошлым периодом, а не в вакууме.
- [ ] Фильтры действуют на все листы, значения по умолчанию осмысленны — дашборд информативен сразу при открытии.
- [ ] Ни круговых диаграмм, ни объёма, ни градиентов.
- [ ] Блок документации: источник, актуальность, определения метрик, владелец.
- [ ] `metriki.md` — определение каждой метрики, включая правило очистки и порог отсечения выбросов с обоснованием.
- [ ] Дашборд грузится меньше 10 секунд, проверено Performance Recorder.
- [ ] Опубликован в Tableau Public, ссылка в README.

Желательные:

- [ ] Есть ответ на вопрос про курьеров: показано, где и когда их не хватает, с оценкой потребности.
- [ ] Есть filter action — фильтрация щелчком по данным, а не только выпадающими списками.
- [ ] Есть параметр, переключающий метрику или горизонт.
- [ ] Найден дефект данных, о котором в ТЗ не сказано.
- [ ] Задвоенные заказы обнаружены и обработаны.
