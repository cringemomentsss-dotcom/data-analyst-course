## Постановка

Маркетинг хочет знать заранее, кто из зарегистрировавшихся дойдёт до первого депозита. Предложение простое: тем, у кого шанс низкий, отправлять письмо с бонусом; тем, у кого высокий, не отправлять — они и так заплатят.

**Задача:** построить модель, предсказывающую, сделает ли зарегистрировавшийся игрок первый депозит.

**Предупреждение, которое стоит прочитать до начала.** Первая модель, которую ты построишь, покажет ROC-AUC около единицы. Это не успех. Разобраться, почему так вышло, и построить модель, которой можно пользоваться, — и есть содержание проекта.

## Что сдать

### 1. Постановка задачи

`postanovka.md`:

- **целевая переменная** словами, с окном наблюдения. «Сделает депозит» — не определение: за какой срок от регистрации;
- **единица наблюдения** — кто строка в выборке;
- **кого исключаем** и почему. Данные кончаются 30 июня; у зарегистрировавшихся в июне окно ещё не закрылось (`check_observation_window` из [тренажёра](../trenazher/zadachi.py));
- **какое решение принимается** по результату модели и **как измеряется успех в деньгах**.

Последний пункт определяет всё остальное, включая выбор метрики и порога.

### 2. Baseline

`baseline.md`. **До модели**, не после. Минимум два:

- константа — доля класса;
- правило в одну строку из здравого смысла.

Зафиксируй метрики. Модель, не обогнавшая правило в одну строку, не нужна: правило понятно бизнесу, не требует переобучения и не ломается.

### 3. Разбор утечки

`utechka.md` — центральный документ проекта.

По каждому признаку из таблицы выше ответь: **известно ли его значение в момент, когда делается прогноз?** Прогноз делается для человека, который только что зарегистрировался.

Три случая, и все три есть в данных:

**Явная утечка.** `sess_total` считается за всю историю. Проверь сам: сколько сессий приходится на время до первого депозита, а сколько после. Число тебя убедит.

**Признак-состояние без времени.** `is_verified` и `vip_level` — текущее состояние, снятое на момент выгрузки. Доля депозитов при `is_verified = 1` — 76,4%, при нуле — 7,7%. Соблазн велик.

Вопрос не «коррелирует ли», а «чему был равен этот флаг в момент регистрации». В данных нет поля, которое бы это сказало.

Правильный вывод здесь — не «это утечка» и не «это хороший признак», а **«использовать нельзя, пока не доказано обратное»**. Разница принципиальна: первое — обвинение без доказательств, второе — беспечность, третье — работа аналитика. Напиши, какой запрос к разработке закрыл бы вопрос за пять минут.

**Честные признаки.** Всё, что случилось до регистрации, плюс первые сутки после — при условии, что прогноз делается через сутки, а не сразу. Это тоже надо оговорить: модель, использующая `sess_24h`, применима не в момент регистрации, а через день.

### 4. Две модели

`model.ipynb` или `.py`:

1. **Модель со всеми признаками** — чтобы увидеть, как выглядит утечка.
2. **Честная модель** — только на признаках, прошедших разбор.

Обе:

- собраны через `Pipeline`, весь препроцессинг внутри;
- разделение выборки **по времени** — регистрации упорядочены, модель применяется к будущему;
- метрика выбрана под задачу, выбор обоснован;
- порог выбран из стоимости ошибок, не 0,5.

Ноутбук обязан проходить `notebook_run_order` из тренажёра спринта 15.

### 5. Записка

`vyvod.md`, страница для маркетинга:

- что модель делает и с какой надёжностью;
- кому отправлять письмо: порог и сколько людей под него попадает;
- сколько это стоит и сколько приносит при названных допущениях;
- **чего от модели ждать не надо**.

## Эталонные числа

Разделение по времени, последние 25% регистраций — тест: 900 в обучении (26,9% положительных), 300 в тесте (25,3%).

| Модель | ROC-AUC | PR-AUC |
|---|---|---|
| Baseline: константа | 0,500 | 0,253 |
| Baseline: правило `sess_24h >= 2` | 0,622 | 0,319 |
| **Со всеми признаками: логрег** | **1,000** | **1,000** |
| **Со всеми признаками: случайный лес** | **1,000** | **1,000** |
| Честная: логрег | **0,856** | 0,750 |
| Честная: случайный лес | 0,847 | 0,685 |

**ROC-AUC равен единице.** Ровно единице, на тестовой выборке, которую модель не видела.

Такого не бывает. Задача, где будущее предсказывается идеально, называется не машинным обучением, а утечкой. Правило, которое стоит унести из спринта: **AUC выше 0,95 — сначала ищи утечку, потом радуйся.**

Честная модель даёт 0,856 — это хороший результат, вдвое лучше baseline по PR-AUC и вполне пригодный для решения о рассылке.

## Ловушки

**1. Случайное разделение вместо временного.** Регистрации упорядочены во времени, модель будет применяться к будущим. Случайное разделение даст завышенную оценку.

**2. Порог 0,5 по умолчанию.** Это не значение по умолчанию, а произвольный выбор. Он оптимален, только когда ошибки стоят одинаково. Здесь не стоят: письмо с бонусом стоит денег, а пропущенный платящий — упущенная выручка.

**3. Accuracy как метрика.** При доле класса 26,6% болван, всегда отвечающий «нет», получает accuracy 73,4%. Смотри на recall и PR-AUC.

**4. Препроцессинг вне пайплайна.** Посчитал медиану и масштабирование на всей выборке — подсмотрел в тест. Кросс-валидация покажет завышенное качество.

**5. Маленькая выборка.** 300 объектов в тесте, из них 76 положительных. Разница в AUC 0,856 и 0,847 на таком объёме — **шум**, а не преимущество одной модели над другой. Прежде чем объявлять победителя, посчитай разброс по кросс-валидации: `cv_score` из тренажёра возвращает его отдельным числом. Это тот же урок, что в спринте 11: число без интервала не сравнивается.

**6. Соблазн подкрутить.** Перебирать модели и признаки, пока метрика на тесте не вырастет, — это подгонка под тест. Тест смотрят один раз, в конце. Всё остальное делается на кросс-валидации.

## Критерии приёмки

**Обязательное**

- [ ] Целевая переменная определена явно, с окном наблюдения.
- [ ] Названо, кого исключаем из-за незакрытого окна, и сколько таких.
- [ ] Baseline построен **до** модели, метрики зафиксированы; их минимум два.
- [ ] Разбор проведён по **каждому** признаку: известно ли значение в момент прогноза.
- [ ] Явная утечка найдена, подтверждена числом из данных.
- [ ] По `is_verified` и `vip_level` сформулирована позиция «нельзя, пока не доказано», названо, какой вопрос это закрывает.
- [ ] Оговорено, в какой момент применима честная модель.
- [ ] Разделение по времени, не случайное.
- [ ] Обе модели собраны через `Pipeline`, препроцессинг внутри.
- [ ] Метрика выбрана под задачу, выбор обоснован; accuracy главной метрикой не является.
- [ ] Порог выбран из стоимости ошибок, значения названы.
- [ ] Приведён разброс по кросс-валидации, а не только среднее.
- [ ] Сказано, можно ли считать одну модель лучше другой на этом объёме данных.
- [ ] Тест использован один раз; описано, как выбиралась модель.
- [ ] Записка для маркетинга: порог, охват, деньги, ограничения.

**Желательное**

- [ ] Кривые обучения и диагноз по ним.
- [ ] Интервал для AUC бутстрапом по тестовой выборке.
- [ ] Проверка, что будет, если применять модель сразу при регистрации, без `sess_24h`.
- [ ] Разбор, какие признаки внесли вклад и в какую сторону.
