# Спринт 0. Git и рабочая среда

**3–4 дня.** Единственный спринт, который не про данные. Он существует, потому что дальше 30 недель всё уходит в репозиторий, и возвращаться настраивать окружение посреди статистики — плохая идея.

Ты Git знаешь. Значит цель не «выучить», а довести до состояния, когда ты про него не думаешь. Разница между этими состояниями — примерно как между «знаю правила дорожного движения» и «вожу».

**На выходе:** публичный репозиторий с рабочим окружением, поднятая база курса, первый коммит с решениями старых SQL-задач.

## Часть 1. Git: модель

### 1.1. Три состояния и три места

Файл в Git живёт в одном из трёх мест:

| Место | Что это | Как посмотреть |
|---|---|---|
| Рабочий каталог | файлы на диске, как ты их видишь | `ls` |
| Индекс (staging) | снимок того, что попадёт в следующий коммит | `git status` |
| Репозиторий | история коммитов | `git log` |

`git add` копирует из рабочего каталога в индекс. `git commit` превращает индекс в коммит. `git checkout` / `git switch` достаёт из репозитория в рабочий каталог.

Ключевое, что чаще всего понимают неправильно: **коммит — это не набор изменений, а полный снимок всего дерева файлов.** Diff, который ты видишь в `git log -p`, вычисляется на лету сравнением двух снимков. Именно поэтому переключение веток мгновенно, а история не «накапливает» изменения.

> **Упражнение 1.1.** Создай пустую папку, `git init`, положи файл, сделай коммит. Потом выполни `git cat-file -p HEAD` — увидишь объект коммита с ссылкой на tree. Дальше `git cat-file -p <хеш_tree>` — увидишь список файлов с хешами blob'ов. Пройди цепочку до содержимого файла. Это займёт три минуты и навсегда закроет вопрос «что Git хранит».

### 1.2. Объектная модель

Четыре типа объектов, всё остальное — надстройка:

- **blob** — содержимое файла. Имени файла в нём нет.
- **tree** — каталог: список имён с указанием, что это (blob или другой tree) и с каким хешем.
- **commit** — указатель на tree плюс автор, дата, сообщение и ссылки на родительские коммиты.
- **tag** — именованный указатель на объект.

Ветка — это **файл с одной строкой**, в которой лежит хеш коммита. Посмотри: `cat .git/refs/heads/main`. Поэтому создание ветки — операция за миллисекунду, а не копирование проекта.

`HEAD` — указатель на текущую ветку (обычно) или прямо на коммит (detached HEAD).

> **Упражнение 1.2.** Выполни `cat .git/HEAD` и `cat .git/refs/heads/main`. Сделай ещё один коммит и посмотри, как изменился второй файл. Ты только что увидел весь механизм веток.

## Часть 2. Повседневный цикл

### 2.1. Смотреть, добавлять, фиксировать

```bash
git status                    # что изменилось, что в индексе
git diff                      # рабочий каталог против индекса
git diff --staged             # индекс против последнего коммита
git add путь                  # добавить в индекс
git add -p                    # добавить по кускам, с просмотром каждого
git commit -m "сообщение"
git log --oneline --graph --decorate --all
```

`git add -p` — недооценённая команда. Она заставляет просмотреть каждое изменение перед коммитом. Половина случайно закоммиченных отладочных `print()` не случилась бы, если бы люди пользовались ею.

> **Упражнение 2.1.** Измени файл в двух местах. Через `git add -p` закоммить только одно из изменений. Проверь `git status` — второе изменение должно остаться незакоммиченным.

### 2.2. Откатить

Три команды с похожими названиями и разным смыслом — источник большинства паник:

| Команда | Что делает | Опасность |
|---|---|---|
| `git restore <файл>` | вернуть файл к состоянию в индексе | несохранённые правки теряются |
| `git restore --staged <файл>` | убрать из индекса, правки в файле сохранить | нет |
| `git reset --soft <коммит>` | сдвинуть ветку, индекс и файлы не трогать | нет |
| `git reset --mixed <коммит>` | сдвинуть ветку и индекс, файлы не трогать | нет (по умолчанию) |
| `git reset --hard <коммит>` | сдвинуть всё, файлы перезаписать | **правки теряются безвозвратно** |
| `git revert <коммит>` | новый коммит, отменяющий указанный | нет, история сохраняется |

Правило: в своей ветке, которую никуда не отправлял, `reset --hard` — нормальный инструмент. В ветке, которую уже отправил и с которой работает кто-то ещё, только `revert`.

И отдельно: `git reflog` помнит, где HEAD был последние 90 дней. Почти всё, что «потерялось», находится там.

> **Упражнение 2.2.** Сделай три коммита. Выполни `git reset --hard HEAD~2`. Убедись, что два коммита исчезли из `git log`. Найди их в `git reflog` и верни через `git reset --hard <хеш>`. Это тот навык, который однажды спасёт полдня работы.

## Часть 3. Ветки и слияния

### 3.1. Создать, переключиться, слить

```bash
git switch -c feature/cohorts     # создать и перейти
git switch main
git merge feature/cohorts
git branch -d feature/cohorts     # удалить слитую
```

Два вида слияния:

- **Fast-forward** — если в основной ветке не было новых коммитов, Git просто передвигает указатель. Merge-коммита не появляется.
- **Merge-коммит** — если обе ветки разошлись, создаётся коммит с двумя родителями.

`git merge --no-ff` заставляет всегда создавать merge-коммит. Многие команды требуют этого, чтобы в истории было видно границы фич.

### 3.2. Rebase

`git rebase main` берёт коммиты твоей ветки и переприкладывает их поверх main, как будто ты начал работу сегодня. История становится линейной и читаемой.

Единственное жёсткое правило: **не делай rebase веток, которые уже кто-то видел.** Rebase переписывает коммиты (у них меняются хеши), и у коллеги, который на них ссылается, всё разъедется.

Для себя, до отправки — rebase хорош. После — нет.

### 3.3. Конфликты

Конфликт возникает, когда две ветки изменили одни и те же строки. Git размечает файл:

```
<<<<<<< HEAD
версия из текущей ветки
=======
версия из вливаемой ветки
>>>>>>> feature/cohorts
```

Разрешение: отредактировать файл до нужного состояния, удалить маркеры, `git add`, потом `git merge --continue` или `git rebase --continue`.

`git merge --abort` возвращает всё как было. Право на отступление — важно знать, что оно есть.

> **Упражнение 3.1.** Создай ветку, измени в ней вторую строку файла. Вернись в main, измени ту же строку иначе. Слей. Разреши конфликт вручную. Потом сделай то же самое, но заверши через `--abort` и убедись, что состояние вернулось.

## Часть 4. Удалённые репозитории

```bash
git remote -v                     # какие удалённые настроены
git fetch origin                  # скачать, ничего не менять локально
git pull                          # fetch + merge (или rebase)
git pull --rebase                 # fetch + rebase
git push -u origin main           # отправить и связать ветку
```

`fetch` безопасен всегда: он только скачивает. `pull` — это `fetch` плюс слияние, и вот оно уже может создать конфликт или лишний merge-коммит.

Многие команды настраивают `git config --global pull.rebase true`, чтобы история не зарастала merge-коммитами вида «Merge branch 'main' into main». Рекомендую поставить.

> **Упражнение 4.1.** Создай пустой репозиторий на GitHub, привяжи локальный, отправь. Потом измени файл через веб-интерфейс GitHub, локально сделай другое изменение в том же файле и попробуй `git push` — получишь отказ. Разреши через `git pull --rebase`.

## Часть 5. Гигиена репозитория аналитика

### 5.1. Что не коммитят

```gitignore
# данные
data/raw/
*.csv
*.parquet
*.db

# секреты
.env
credentials*.json

# python
__pycache__/
.venv/
.ipynb_checkpoints/

# macos
.DS_Store
```

Три причины не класть данные в Git: репозиторий раздувается навсегда (удаление файла из истории не уменьшает её), Git не умеет диффить бинарники, и на реальных данных это ещё и вопрос безопасности.

Что делать вместо: данные лежат локально или в объектном хранилище, а в репозитории — **скрипт, который их получает или генерирует.** Ровно так устроена база этого курса: `generate.py` в репозитории, CSV — нет.

### 5.2. Если секрет уже улетел

Удалить файл следующим коммитом — недостаточно: он остаётся в истории и доступен по хешу. Порядок действий:

1. **Первым делом отозвать сам секрет.** Ключ, попавший в публичный репозиторий, считается скомпрометированным, даже если репозиторий висел пять минут.
2. Переписать историю: `git filter-repo --path файл --invert-paths` (или BFG Repo-Cleaner).
3. Force-push и предупредить всех, у кого есть копия.

Порядок именно такой. Чистить историю, не отозвав ключ, бессмысленно.

### 5.3. Сообщения коммитов

Плохо: `fix`, `update`, `wip`, `изменения`.
Хорошо: `Исправлен двойной счёт в когортном отчёте: JOIN размножал строки по сессиям`.

Правило: сообщение отвечает на вопрос «что изменится в поведении», а не «какие файлы я трогал» — файлы и так видны в диффе.

Формат, который стоит взять: первая строка до 72 символов, повелительное наклонение, потом пустая строка и абзац с «почему», если неочевидно.

### 5.4. Ноутбуки в Git

Главная боль. `.ipynb` — это JSON, внутри которого лежит и код, и вывод, и метаданные счётчиков. Последствия:

- diff нечитаем: изменение одной строки кода выглядит как изменение половины файла;
- конфликты в ноутбуках практически неразрешимы вручную;
- в выводе могут оказаться данные, которые не должны попасть в публичный репозиторий.

Решение — очищать вывод перед коммитом. Настраивается один раз:

```bash
pip install nbstripout
nbstripout --install          # ставит фильтр в .git/config текущего репозитория
```

После этого Git будет коммитить ноутбуки без вывода, а локально ты видишь вывод как обычно.

> **Упражнение 5.1.** Поставь `nbstripout` в репозиторий курса. Создай ноутбук, выполни ячейку с выводом, закоммить. Проверь `git show HEAD:путь.ipynb | grep outputs` — вывод должен быть пуст.

## Часть 6. Среда

### 6.1. Что ставим

| Что | Зачем | Как |
|---|---|---|
| Docker Desktop | PostgreSQL, потом ClickHouse и Airflow | [docker.com](https://www.docker.com/products/docker-desktop/), сборка Apple Silicon |
| Python 3.12+ | анализ | уже стоит |
| venv | изоляция зависимостей | встроен в Python |
| JupyterLab | ноутбуки | из `requirements.txt` |
| DBeaver | клиент к базам | [dbeaver.io](https://dbeaver.io/), Community Edition |
| VS Code | код и SQL | уже настраивал в августе |

**Про диск.** На машине сейчас около 14 ГБ свободно. PostgreSQL займёт ~0,5 ГБ, но к модулю 6 добавятся ClickHouse (~1 ГБ), Spark (~1,5 ГБ) и Airflow (~2 ГБ). До февраля место освободить придётся — имей в виду заранее, а не когда `docker pull` упадёт посреди спринта.

### 6.2. Поднять базу

Всё уже собрано в корне курса. Порядок:

```bash
cd "resources/da-course"
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
make db
```

`make db` поднимает контейнер PostgreSQL, генерирует данные и заливает их. Занимает пару минут. Проверка:

```bash
make check
```

Должно вывести 15 таблиц. Подключение из DBeaver: хост `localhost`, порт `5433`, база `casino`, пользователь `analyst`, пароль `analyst`, схема `casino`.

> **Упражнение 6.1.** Подключись из DBeaver, выполни `SELECT count(*) FROM casino.visitors;` — должно быть 289 708. Потом `make down`, убедись что подключение отвалилось, `make up` — вернулось. Данные на месте: они в volume, а не в контейнере.
