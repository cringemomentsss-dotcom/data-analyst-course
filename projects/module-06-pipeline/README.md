# Итоговый проект модуля 6. Сквозной пайплайн

**1 неделя, ~30 часов.** Итоговый проект модуля инженерии данных и самая инженерная работа курса.

Четыре спринта модуля дали четыре куска: оптимизацию и слои хранилища, ClickHouse, PySpark, Airflow. Здесь они собираются в одну работающую систему.

**Главное требование:** пайплайн разворачивается **из чистого состояния одной командой** и работает. Не «у меня локально запускалось», а `make` на пустой машине.

---

## Постановка

Ты — единственный аналитик в «Потоке+». Дата-инженера нет и не будет ещё полгода. Сырые события копятся в объектном хранилище, продукту нужен дашборд, который обновляется сам.

**Задача:** построить и оформить систему, которую сможет поднять и поддерживать человек, который её не писал.

Это и есть выпускная работа модуля: она проверяет не отдельные навыки, а способность собрать их так, чтобы получилось нечто, что работает без тебя.

---

## Что построить

```
MinIO (raw, JSON)
      │  сенсор ждёт партицию
      ▼
PySpark ──► staging (Parquet) ──► core ──► mart (Parquet)
      │                                       │
      │  тесты качества на каждом слое        │
      ▼                                       ▼
   отчёт о качестве                     ClickHouse
                                              │
                                              ▼
                                     CSV-витрина → дашборд

                 всё оркестровано Airflow
```

### Слои

Слои из спринта 16, теперь по-настоящему:

| Слой | Что в нём | Формат |
|---|---|---|
| `raw` | сырьё как приехало, ничего не меняется | JSON.gz в MinIO |
| `staging` | разобрано по схеме, типизировано, битое отделено | Parquet в MinIO |
| `core` | очищено, дедуплицировано, обогащено справочниками | Parquet в MinIO |
| `mart` | агрегаты под конкретный дашборд | Parquet + ClickHouse |

**Бизнес-логика живёт в одном слое.** Определение «активного пользователя» — в `core`, а не в трёх витринах по-своему.

### Оркестрация

DAG, запускающийся по расписанию, с сенсором, retry, уведомлениями и возможностью пересчитать любой прошлый день.

### Качество

Тесты на данные **на каждом слое** — по образцу первой части тренажёра спринта 15. Минимум на каждом слое:

- уникальность ключа;
- отсутствие пропусков в обязательных полях;
- сходимость с предыдущим слоем.

Провал теста уровня `error` останавливает пайплайн. Провал уровня `warn` — пишет предупреждение и пропускает дальше.

### Дашборд

Здесь придётся принять решение и объяснить его.

**Tableau Public не подключается к базам данных** — только файлы и Google Таблицы. Значит «дашборд обновляется автоматически» реализуемо ровно одним способом: DAG кладёт CSV туда, откуда Tableau умеет забирать по расписанию, то есть в Google Таблицу.

От тебя нужно:

- реализовать выгрузку витрины в CSV задачей DAG;
- описать цепочку до дашборда целиком и честно назвать, где она рвётся и почему;
- сказать, как это выглядело бы на платном Tableau, Metabase или Superset.

Разбор ограничения ценнее, чем обход. Аналитик, который умеет назвать, чего инструмент не может, экономит команде месяц.

## Что сдать

### 1. Работающая система

```
solutions/
├── Makefile           или скрипт: одна команда поднимает всё
├── dags/              DAG-и
├── pipeline/          скрипты PySpark
├── sql/               DDL и загрузка в ClickHouse
├── tests/             тесты качества данных
└── mart/              выгрузка CSV
```

### 2. `README.md`: как запустить

Инструкция для человека, который видит проект впервые. Проверяется буквально: я беру чистую машину, ставлю Docker, клонирую и делаю по README.

Обязательно: требования к ресурсам. Сколько нужно памяти Docker и места на диске — числами.

### 3. `architecture.md`: решения и альтернативы

Главный документ проекта. По каждому решению: что выбрал, почему, **какая была альтернатива и чем она хуже здесь**.

Минимум разобрать:

| Решение | Альтернативы |
|---|---|
| Parquet для промежуточных слоёв | ORC, CSV, писать сразу в ClickHouse |
| `ORDER BY` витрины в ClickHouse | другие столбцы, другой порядок |
| Партиционирование по дню | по месяцу, без партиций |
| Обработка опоздавших событий | выбросить, пересчитать партицию, отдельная таблица |
| Оркестрация по расписанию | по датасету, по сенсору |
| Слои раздельно | считать витрину из raw одним запросом |
| SequentialExecutor | LocalExecutor, Celery |

Пункт «чем альтернатива хуже **здесь**» — обязателен. Не «ORC хуже Parquet», а «ORC не хуже, но экосистема вокруг Parquet шире, а выигрыша на наших объёмах нет».

### 4. `pipeline.md`: схема и слои

Схема пайплайна (картинка или текстом), описание каждого слоя: что в нём, зернистость, кто владелец, частота обновления, SLA.

Плюс **lineage**: какая витрина из чего собрана и что сломается, если изменить источник.

### 5. `quality.md`: качество данных

Какие тесты стоят на каком слое, какие блокируют, какие предупреждают, и почему именно так. Плюс отчёт по последнему прогону: сколько строк на каждом слое.

### 6. `runbook.md`: что делать, когда сломалось

Страница для дежурного:

- пайплайн не отработал ночью — порядок действий;
- какие задачи безопасно перезапустить;
- как пересчитать день задним числом;
- как понять, что данные неполны, а не отсутствуют;
- кого будить и в каком случае.

## Ограничения окружения

Названы честно, потому что упрёшься в них в первый же день.

**Память.** Airflow ~1,4 ГБ, ClickHouse ~0,6 ГБ, MinIO ~0,15 ГБ. При типовых 3,8 ГБ на весь Docker одновременный запуск Airflow, Spark-задачи и ClickHouse — на грани. Падение с кодом 137 — это OOM, а не ошибка в коде.

Варианты: добавить Docker памяти в настройках; гасить лишнее через `make module6-down`; запускать Spark с `--driver-memory 1600m`.

**Диск.** Схема `dwh` в PostgreSQL — 1,5 ГБ, ClickHouse — ещё около 250 МБ, сырьё в MinIO — 50 МБ, плюс образы. Держи 10 ГБ свободными.

**Первый запуск Spark** качает 275 МБ jar-ов с Maven. Это может занять минуты. Дальше они в кэше на томе.

**SequentialExecutor** выполняет задачи по одной. Параллельность в DAG будет объявлена, но не реализована — и это надо назвать в `architecture.md`.

## Критерии приёмки

**Обязательное**

- [ ] Система разворачивается из чистого состояния одной командой; проверено на снесённых томах.
- [ ] В README указаны требования к памяти и диску, числами.
- [ ] Четыре слоя разделены, у каждого своя зернистость и назначение.
- [ ] Бизнес-логика не продублирована между слоями.
- [ ] Схема датафрейма задана явно; `inferSchema` не используется.
- [ ] Тесты качества данных есть на каждом слое.
- [ ] Разделены блокирующие и предупреждающие проверки, выбор объяснён.
- [ ] Сходимость слоёв проверяется тестом, а не глазами.
- [ ] Числа в ClickHouse совпадают с числами в Parquet, проверено тестом.
- [ ] DAG идемпотентен; показано двумя прогонами за одну дату.
- [ ] Есть сенсор с таймаутом.
- [ ] Настроены retry и уведомление об ошибке.
- [ ] Backfill за прошлый период отрабатывает; результат описан.
- [ ] Секреты в Connections, в коде их нет.
- [ ] Витрина выгружается в CSV задачей DAG.
- [ ] Цепочка до дашборда описана целиком, включая место, где она рвётся.
- [ ] `architecture.md`: по каждому решению названа альтернатива и почему она хуже **здесь**.
- [ ] `pipeline.md`: схема, слои, lineage.
- [ ] `runbook.md`: что делать при ночном падении.
- [ ] Ограничение SequentialExecutor названо и объяснено.

**Желательное**

- [ ] Пайплайн обрабатывает опоздавшие события пересчётом партиций, а не выбрасыванием.
- [ ] Мониторинг метрик витрины: алерт на аномальное изменение.
- [ ] Второй DAG — перезаливка, независимый от основного.
- [ ] Датасеты вместо расписания хотя бы на одном участке.
- [ ] Замер: сколько времени занимает полный прогон и что на критическом пути.
- [ ] Оценка, что сломается при десятикратном росте данных.

## Что это даёт в портфолио

Единственный проект курса, который показывает работу с инфраструктурой целиком. На собеседовании на позицию сильнее джуна про него спросят подробнее, чем про все дашборды вместе.

Три вопроса, к которым стоит подготовиться:

- почему слои разделены, а не считается всё одним запросом;
- что произойдёт, если источник опоздает на шесть часов;
- как понять, что витрина неполна, если пайплайн отработал «успешно».
