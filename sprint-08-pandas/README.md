## Часть 1. Модель pandas

### 1.1. Series и DataFrame

**Series** — одномерный массив с индексом. **DataFrame** — таблица из нескольких Series с общим индексом.

```python
import pandas as pd

s = pd.Series([1400, 2100, 900], index=["a", "b", "c"])
df = pd.DataFrame({"price": [1400, 2100], "master": ["Иван", "Тимур"]})
```

Ключевое, чего нет в SQL: **индекс**. Это не то же, что первичный ключ — индекс не обязан быть уникальным, участвует в выравнивании при операциях и легко превращается в источник загадочных ошибок. Практическое правило на первое время: **после фильтраций и группировок вызывай `.reset_index(drop=True)`**, если не собираешься использовать индекс осмысленно.

### 1.2. Что смотреть сразу после загрузки

```python
df.shape          # (строк, столбцов)
df.info()         # типы, число непустых, память
df.head(10)
df.describe()     # числовая сводка
df.dtypes
df.isna().sum()   # пропуски по столбцам
df.nunique()      # уникальных значений по столбцам
```

Первые пять минут работы с любой новой выгрузкой — это `info()`, `isna().sum()`, `nunique()` и `describe()`. Именно в таком порядке.

### 1.3. Загрузка

```python
df = pd.read_csv("data.csv", dtype=str, keep_default_na=False, encoding="utf-8")
```

Два аргумента, которые стоит ставить по умолчанию при работе с грязными данными:

**`dtype=str`** — читать всё как строки. Без него pandas угадывает типы, и угадывает иногда правильно, а иногда превращает `id` из `'00123'` в `123`, ломая соединения. Типы приводим сами, осознанно, после того как посмотрели на данные.

**`keep_default_na=False`** — не превращать `NA`, `null`, `N/A`, `NaN`, пустую строку и ещё десяток вариантов в `NaN` автоматически. Сначала надо **увидеть**, чем именно обозначены пропуски: это диагностика источника. Один поставщик пишет `null`, другой `-`, третий `н/д` — и это разная информация.

Другие полезные аргументы: `sep=";"` для европейского CSV, `decimal=","`, `parse_dates=["col"]`, `nrows=1000` для быстрого просмотра большого файла, `usecols=[...]` чтобы не тащить лишнее.

Чтение из базы напрямую тоже возможно и часто удобнее файлов:

```python
from sqlalchemy import create_engine
engine = create_engine("postgresql+psycopg2://analyst:analyst@localhost:5433/casino")
df = pd.read_sql("SELECT * FROM casino.deposits WHERE status = 'success'", engine)
```

Правило то же, что для Tableau: **агрегируй в базе, тащи в pandas результат.** `SELECT *` с миллионами строк — почти всегда ошибка.

## Часть 2. Типы данных

### 2.1. Что бывает

| Тип | Что | Замечание |
|---|---|---|
| `int64`, `float64` | числа | пропуск возможен только во `float`, поэтому целочисленный столбец с NaN становится float |
| `str` | строки | в pandas 3 это отдельный тип, не `object` |
| `object` | что угодно | если видишь `object` там, где ждал число, — в столбце мусор |
| `bool` | флаги | |
| `datetime64[ns]` | момент времени | |
| `timedelta64[ns]` | промежуток | результат вычитания дат |
| `category` | категория | экономит память и ускоряет группировку |

Диагностика номер один: **столбец, который должен быть числом, имеет тип `object` или `str`.** Значит в нём есть хоть одно нечисловое значение, и все арифметические операции по нему либо упадут, либо дадут ерунду.

### 2.2. Приведение

```python
pd.to_numeric(s, errors="coerce")     # что не разобралось → NaN
pd.to_datetime(s, errors="coerce")
s.astype("float64")                   # упадёт на первом мусоре
s.astype("category")
```

`errors="coerce"` — рабочий режим для грязных данных: вместо падения ставит `NaN`, и дальше можно посмотреть, сколько именно не разобралось. `errors="raise"` (по умолчанию) полезен, когда ты уверен, что данные чистые, и хочешь узнать, если это не так.

### 2.3. Ловушка dayfirst

```python
pd.to_datetime("2026-03-01", dayfirst=True)     # 2026-01-03 !
```

`dayfirst=True` применяется и к ISO-строкам. Если в столбце смешаны `2026-03-01` и `01.03.2026`, разбор с одним флагом на всех испортит одну из групп — **молча, без ошибки**. Проверить легко: посмотреть `df["date"].min()` и `max()` — вылезут даты за пределами периода.

Правильно — разбирать форматы по отдельности: ISO через `format="ISO8601"`, остальное с `dayfirst=True`.

Это задача 4 тренажёра, и она там не для красоты: ровно эта ошибка испортит любой временной отчёт.

### 2.4. Строковые методы

Доступны через `.str`:

```python
s.str.strip().str.lower()
s.str.replace(" USD", "", regex=False)
s.str.replace(r"[^\d.,]", "", regex=True)
s.str.contains("роботы", na=False)
s.str.split(" ", expand=True)          # в несколько столбцов
```

`.str` работает по всему столбцу сразу, без цикла. Забыть `.str` и написать `s.lower()` — частая ошибка первого дня.

## Часть 3. Индексация и фильтрация

### 3.1. loc и iloc

```python
df.loc[0, "price"]           # по МЕТКЕ индекса и имени столбца
df.iloc[0, 2]                # по ПОЗИЦИИ
df.loc[df["price"] > 1000, ["price", "master"]]
df.loc[:, "price"]           # весь столбец
```

`loc` — по метке, `iloc` — по номеру. Они совпадают, пока индекс — это `0, 1, 2, …`, и расходятся сразу после первой фильтрации, потому что индекс сохраняет исходные метки. Отсюда классическая путаница: `df.iloc[0]` после фильтрации даст первую строку выборки, а `df.loc[0]` — упадёт, если строки с меткой 0 в выборке нет.

Правило: **`loc` по умолчанию, `iloc` только когда действительно нужна позиция.**

### 3.2. Булева индексация

```python
df[df["status"] == "paid"]
df[(df["price"] > 100) & (df["country"] == "DE")]
df[df["country"].isin(["DE", "US"])]
df[df["price"].between(100, 500)]
df[df["promo_code"].notna()]
df.query("price > 100 and country == 'DE'")
```

Две вещи, которые надо запомнить сразу:

- операторы `&`, `|`, `~` — не `and`, `or`, `not`;
- **скобки вокруг каждого условия обязательны**, потому что приоритет `&` выше, чем у `>`.

`df[a > 1 & b < 2]` — синтаксическая ошибка или, хуже, неверный результат.

### 3.3. Copy-on-Write: главное изменение pandas 3

В pandas 2 и раньше присваивание в срез выдавало `SettingWithCopyWarning` — предупреждение, знаменитое тем, что его никто не читал.

В pandas 3 **предупреждения нет вообще**. Copy-on-Write включён всегда и отключить его нельзя. Поведение такое:

```python
sub = df[df["price"] > 100]
sub["price"] = 0          # не падает, не предупреждает
# df не изменился. sub изменился.
```

Это яснее, чем раньше: срез — всегда независимая копия, исходные данные через него не испортить. Но появилась новая ловушка: **если ты рассчитывал изменить `df`, изменение потерялось, и никто тебе об этом не сказал.**

Правильно менять исходный DataFrame через `loc`:

```python
df.loc[df["price"] > 100, "price"] = 0
```

Практическое следствие: увидев в чужом коде или в статье совет «делай `.copy()`, чтобы избежать SettingWithCopyWarning» — знай, что это про старую версию. В pandas 3 копия и так гарантирована.

### 3.4. Цепочки методов

```python
result = (
    df
    .loc[df["status"] == "paid"]
    .assign(price=lambda d: pd.to_numeric(d["price"], errors="coerce"))
    .dropna(subset=["price"])
    .groupby("category", dropna=False)["price"]
    .sum()
    .sort_values(ascending=False)
)
```

Читается сверху вниз как последовательность шагов — та же логика, что CTE в SQL. `assign` добавляет столбец внутри цепочки, `lambda d:` ссылается на промежуточный результат.

Альтернатива — двадцать промежуточных переменных `df1`, `df2`, `df_clean`, `df_clean2`, в которых через час не разберёшься. Цепочки лучше, но не бесконечные: три-семь шагов, потом присваивание в осмысленно названную переменную.

## Часть 4. Пропуски

### 4.1. Найти

```python
df.isna().sum()                                  # по столбцам
df.isna().sum().sort_values(ascending=False)
(100 * df.isna().mean()).round(1)                # в процентах
df[df["country"].isna()]                         # сами строки
```

### 4.2. Неявные пропуски

Хуже явных, потому что `isna()` их не видит:

- пустая строка `''`;
- текстовые заглушки: `'null'`, `'-'`, `'н/д'`, `'не указано'`, `'unknown'`;
- числовые заглушки: `0`, `-1`, `9999`, `1900-01-01`;
- пробел.

Поэтому и нужен `keep_default_na=False` при загрузке: сначала увидеть все варианты (`s.value_counts()` покажет), потом привести к `NaN` осознанно. Это задача 2 тренажёра.

Числовые заглушки — отдельная беда: `0` в столбце «длительность» может значить и «ноль секунд», и «не записалось». Отличить можно только зная предметную область. В нашей игре нулевая длительность сессии — это баг клиента, а нулевая цена бонуса — настоящий ноль.

### 4.3. Что делать

| Стратегия | Когда | Как |
|---|---|---|
| Оставить | пропуск — это информация | ничего не делать, но помнить про `dropna=False` в группировках |
| Отдельная категория | категориальный столбец | `fillna("не указано")` |
| Удалить строки | пропуск в ключевом поле, доля мала | `dropna(subset=["price"])` |
| Удалить столбец | пропусков больше 60–70% | `drop(columns=[...])` |
| Заполнить константой | ноль осмысленен | `fillna(0)` |
| Заполнить по группе | есть похожие объекты | `groupby("cat")["price"].transform("median")` |

Главное правило: **у каждого решения по пропускам должно быть обоснование, записанное словами.** Не «заполнил медианой», а «заполнил медианой по категории, потому что цена внутри категории однородна, а пропусков 4% и удалять их значило бы потерять целый сегмент».

Заполнение по группе — самый содержательный приём:

```python
df["price"] = df["price"].fillna(
    df.groupby("category")["price"].transform("median")
)
```

`transform` возвращает Series той же длины, что исходный, — в отличие от `agg`, который возвращает по строке на группу. Это различие стоит запомнить: половина ошибок с `groupby` именно здесь.

### 4.4. Чего не делать

**Не заполнять средним, не подумав.** Среднее чувствительно к выбросам; на распределении с хвостом (деньги, время) медиана честнее.

**Не заполнять нулями числовые метрики.** Ноль — это значение, и он попадёт в средние, занизив их. Разница между «не знаем» и «ноль» существенна.

**Не удалять строки, не посчитав, сколько теряешь и кого.** Если пропуски в `country` сосредоточены в одной стране, `dropna` выкинет её целиком и сместит все выводы.

## Часть 5. Дубликаты

```python
df.duplicated().sum()                          # полные дубликаты
df.duplicated(subset=["a", "b"]).sum()         # по смысловому ключу
df[df.duplicated(subset=["a"], keep=False)]    # ВСЕ строки дубликатных групп
df.drop_duplicates(subset=["a", "b"], keep="first")
```

`keep=False` в `duplicated` — для просмотра: показывает все копии, а не только повторные. Полезно, чтобы понять, чем именно копии отличаются.

### 5.1. Что считать дубликатом

Решение аналитика, и оно не сводится к `df.duplicated()`.

Полное совпадение всех столбцов — почти всегда дубликат. Но в реальных выгрузках у копий отличается технический идентификатор, так что искать надо по **смысловому ключу**: что именно означает «та же сущность».

В наших данных: одна и та же покупка — это (игрок, предмет, время, цена). Один и тот же игрок — все атрибуты, кроме `player_id`.

### 5.2. Цена дедупликации

Здесь важное, о чём почти не пишут в учебниках.

В данных проекта 12 130 строк игроков, из которых 130 — искусственные копии. После дедупликации по всем атрибутам кроме идентификатора остаётся **11 998**, а не 12 000. Два игрока склеились потому, что у них случайно совпали все атрибуты: дата регистрации, страна, платформа, канал, число сессий, минуты, уровень.

Это не ошибка твоего кода. Это **неизбежная цена дедупликации по признакам вместо идентификатора**: убирая мусор, ты всегда рискуешь склеить два настоящих объекта. Правильный ответ — не «избежать», а **посчитать масштаб риска и назвать его в отчёте**: «дедупликация удалила 132 строки, из них не менее двух — вероятно, настоящие игроки с совпавшими атрибутами; погрешность 0,02%, на выводы не влияет».

Аналитик, который приводит такую оценку, отличается от аналитика, который пишет «удалил дубликаты».

### 5.3. Неявные дубликаты

Те же, что в спринте 1 и 3, только в pandas:

```python
df["country"].value_counts()                  # увидеть варианты
df["country"] = df["country"].str.strip().str.upper()
df["country"] = df["country"].replace({"GERMANY": "DE", "GER": "DE"})
```

И то же ограничение: регистр и пробелы автоматика чинит, а `Germany` → `DE` требует таблицы соответствий, написанной человеком.

## Часть 6. Категоризация и агрегация

### 6.1. Векторизация против apply

```python
# медленно: apply вызывает функцию на каждой строке
df["with_vat"] = df["price"].apply(lambda x: x * 1.2)

# быстро: одна операция над всем массивом
df["with_vat"] = df["price"] * 1.2
```

Разница на сотнях тысяч строк — секунды против минут. Причина: векторные операции выполняются в скомпилированном коде, `apply` — в питоне, построчно.

Что использовать вместо `apply`:

| Вместо | Бери |
|---|---|
| арифметика в apply | обычные операторы над Series |
| условие в apply | `np.where(cond, a, b)` или `.mask()` / `.where()` |
| несколько условий | `np.select([c1, c2], [v1, v2], default=v3)` |
| замена значений | `.replace()`, `.map()` |
| бакеты | `pd.cut()`, `pd.qcut()` |
| строки | методы `.str` |

`apply` остаётся оправданным, когда логика действительно построчная и сложная — например, разбор JSON из столбца. Но это редкость, и `apply` должен быть осознанным выбором, а не привычкой.

Отдельно: **`iterrows()` — антипаттерн.** Он медленный и возвращает копии, поэтому изменения через него теряются. Если тянет написать `for i, row in df.iterrows()`, почти наверняка нужна векторная операция.

Ещё: `applymap` в pandas 3 **удалён**. Вместо него `DataFrame.map()`.

### 6.2. cut и qcut

```python
# фиксированные границы
df["bucket"] = pd.cut(df["price"], bins=[-np.inf, 20, 50, 100, np.inf],
                      labels=["до 20", "20-50", "50-100", "100+"], right=False)

# равные по числу наблюдений — квантили
df["decile"] = pd.qcut(df["ltv"], q=10, labels=False)
```

`right=False` — левый край включается, правый нет; так же, как в бакетах из спринта 3. По умолчанию наоборот, и это источник расхождения на границах.

`qcut` — то же, что `NTILE` в SQL: децили плательщиков по сумме.

### 6.3. groupby

```python
df.groupby("category", dropna=False)["price"].sum()
df.groupby(["category", "country"])["price"].agg(["count", "sum", "mean", "median"])
df.groupby("category").agg(
    orders=("order_id", "nunique"),
    revenue=("price", "sum"),
    avg_price=("price", "mean"),
)
```

**`dropna=False` — почти всегда нужен.** По умолчанию `groupby` **выбрасывает** строки с пропущенным ключом, молча. В нашей игре у 716 игроков не заполнена страна: группировка по умолчанию их потеряет, и сумма по странам не сойдётся с общей — а понять, почему, будет непросто.

Именованная агрегация (третий пример) читается лучше всего и сразу даёт понятные имена столбцов.

### 6.4. agg против transform

```python
df.groupby("cat")["price"].agg("mean")        # по строке на группу
df.groupby("cat")["price"].transform("mean")  # той же длины, что df
```

`agg` схлопывает, `transform` — нет. `transform` нужен, когда результат группировки надо приписать каждой строке: доля от суммы по группе, отклонение от среднего по группе, заполнение пропусков медианой группы.

Это ровно различие между `GROUP BY` и оконной функцией из спринта 4. Если понял там — понял и здесь.

### 6.5. Сводные таблицы

```python
df.pivot_table(index="city", columns="month", values="amount",
               aggfunc="sum", fill_value=0, margins=True)
```

`fill_value=0` — чтобы пустые комбинации были нулями, а не `NaN`: иначе в отчёте появятся дырки там, где на самом деле нули. `margins=True` добавит итоговую строку и столбец.

## Часть 7. Соединения

```python
pd.concat([df1, df2], ignore_index=True)          # по строкам, как UNION ALL
pd.concat([df1, df2], axis=1)                     # по столбцам

df.merge(other, on="player_id", how="left")
df.merge(other, left_on="id", right_index=True, how="left")
```

`how`: `inner`, `left`, `right`, `outer` — те же джойны, что в SQL, с теми же ловушками.

### 7.1. validate — лучший аргумент merge

```python
df.merge(other, on="player_id", how="left", validate="one_to_one")
```

Возможные значения: `one_to_one`, `one_to_many`, `many_to_one`, `many_to_many`.

Если фактическая кардинальность не совпадает с заявленной, `merge` **упадёт с ошибкой** вместо того, чтобы молча размножить строки. Это ловит fan-out автоматически — то самое, что в SQL приходится проверять руками через сравнение `count(*)` до и после.

Ставь `validate` всегда. Тридцать символов, которые экономят день отладки неверных сумм.

### 7.2. Проверка после соединения

Даже с `validate` полезна привычка:

```python
before = len(df)
df = df.merge(other, on="key", how="left", validate="many_to_one")
assert len(df) == before, f"строк стало {len(df)} вместо {before}"
print("не нашлось пар:", df["other_col"].isna().sum())
```

Вторая строка важна не меньше первой: `left join` не размножил строки, но мог не найти пары — и тогда в столбцах справа `NaN`, а метрика по ним занижена.

### 7.3. Индикатор

```python
df.merge(other, on="key", how="outer", indicator=True)["_merge"].value_counts()
```

Добавляет столбец со значениями `left_only`, `right_only`, `both`. Быстрый способ понять, насколько два набора данных пересекаются, — и первое, что стоит сделать при расхождении цифр между двумя источниками.

## Часть 8. Время

```python
df["ts"] = pd.to_datetime(df["ts"], errors="coerce")
df["ts"].dt.date, df["ts"].dt.year, df["ts"].dt.month
df["ts"].dt.dayofweek          # 0 = понедельник
df["ts"].dt.to_period("M")     # период-месяц
df["ts"].dt.floor("D")         # усечение, аналог date_trunc

df.set_index("ts").resample("MS")["amount"].sum()   # по месяцам
df.set_index("ts").resample("W-MON")["amount"].sum()  # по неделям с понедельника
```

`resample` — это `date_trunc` плюс группировка одной операцией. Работает только когда индекс — даты.

**Пропущенные периоды.** `resample` возвращает непрерывный ряд внутри диапазона данных — то есть февраль появится, даже если данных за февраль нет. Это уже лучше, чем `GROUP BY` в SQL. Но если данные начинаются с марта, а отчёт нужен с января, придётся дотянуть через `reindex`:

```python
full = pd.date_range("2026-01-01", "2026-06-01", freq="MS")
s = s.reindex(full, fill_value=0)
```

## Часть 9. Ноутбук как документ

### 9.1. Правила

1. **Структура.** Заголовки markdown: постановка, данные, качество, обработка, выводы. Ноутбук читается сверху вниз как текст, а не как свалка ячеек.
2. **Текст между ячейками.** Перед блоком кода — что делаем и зачем. После — что получилось. Ноутбук из двухсот ячеек кода без единой строки текста не читает никто, включая автора через месяц.
3. **Перезапускается с нуля.** `Kernel → Restart & Run All` должен пройти без ошибок. Если не проходит — значит результат зависит от порядка, в котором ты случайно нажимал ячейки, и воспроизвести его нельзя.
4. **Номера ячеек по порядку.** `[47]`, `[12]`, `[103]` вперемешку — признак того, что пункт 3 не выполняется.
5. **Никаких путей вида `/Users/IlyaKrut/...`.** Только относительные: у меня такого пути нет.
6. **Вывод чистится перед коммитом** — `nbstripout` из спринта 0 делает это сам.

### 9.2. Что должно остаться после ноутбука

Ноутбук — это черновик исследования. Результат работы — три вещи:

- **обработанные данные** (файл или таблица в базе);
- **отчёт** словами, отдельным файлом;
- **функции**, которые понадобятся ещё раз, вынесенные в `.py` и импортируемые.

Ноутбук как единственный носитель результата — плохая практика: его нельзя переиспользовать, протестировать и запустить по расписанию.
