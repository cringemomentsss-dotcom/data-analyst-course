Разница между диалектами не косметическая. SQLite — встраиваемая база с динамической типизацией и минимумом функций. PostgreSQL — полноценная СУБД со строгими типами, богатой библиотекой функций, планировщиком запросов и десятками возможностей, которых в SQLite нет вовсе. На рынке спрашивают Postgres.

## Часть 1. Базы данных и СУБД

### 1.1. Что делает СУБД

База данных — это данные. СУБД — программа, которая ими управляет. Разница существенна: SQL вы пишете не базе, а СУБД, и от неё зависит, что вообще возможно.

Четыре вещи, которые делает СУБД и которые нельзя получить, храня данные в файлах:

1. **Транзакции.** Либо все изменения применились, либо ни одно. Перевод денег между счетами не может остановиться посередине.
2. **Конкурентный доступ.** Сто человек читают и пишут одновременно, и никто не видит полуприменённых изменений.
3. **Целостность.** Внешний ключ не даст записать ставку несуществующего игрока.
4. **Планировщик.** Ты описываешь, что хочешь получить; СУБД сама решает, как это посчитать быстрее всего. Именно поэтому SQL — декларативный язык.

### 1.2. OLTP и OLAP

| | OLTP | OLAP |
|---|---|---|
| Для чего | работа продукта | анализ |
| Запросы | много мелких, точечных | мало, но тяжёлых |
| Пример | «покажи баланс игрока 1423» | «оборот по категориям за полгода» |
| Хранение | построчное | поколоночное |
| Кто | PostgreSQL, MySQL | ClickHouse, BigQuery, Snowflake |

Аналитик почти никогда не пишет запросы в боевую OLTP-базу продукта: тяжёлый аналитический запрос может положить продакшн. Данные копируют в аналитическое хранилище — этим занимается дата-инженер, а как устроен этот процесс, разберём в модуле 6.

В нашем курсе PostgreSQL используется как аналитическая база. Это нормально до определённых объёмов: до десятков миллионов строк Postgres справляется. Дальше начинается ClickHouse.

### 1.3. Схемы

В PostgreSQL внутри базы есть **схемы** — пространства имён для таблиц. У нас всё лежит в схеме `casino`, а не в `public`.

Поэтому в начале сессии:

```sql
SET search_path TO casino, public;
```

Либо писать полное имя: `casino.users`. В SQLite схем не было, и это первое, обо что спотыкаются при переходе.

> **Упражнение 1.1.** Подключись и выполни `SELECT count(*) FROM users;` без `SET search_path`. Получишь ошибку. Потом с `SET`. Потом `SELECT count(*) FROM casino.users;`. Три способа, один результат.

## Часть 2. Порядок выполнения запроса

### 2.1. Логический порядок

Пишешь ты в одном порядке, выполняется в другом:

```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

Из этого следует всё остальное:

- В `WHERE` нельзя сослаться на алиас из `SELECT` — `SELECT` ещё не выполнялся.
- В `ORDER BY` — можно: он идёт после `SELECT`.
- `WHERE` фильтрует строки до группировки, `HAVING` — группы после.
- Оконные функции считаются между `SELECT` и `DISTINCT`, поэтому фильтровать по ним в `WHERE` нельзя, нужен подзапрос или CTE.

Это не правила, которые надо запомнить. Это следствия одной схемы, которую надо понять один раз.

> **Упражнение 2.1.** Попробуй `SELECT amount_eur * 2 AS double_amount FROM deposits WHERE double_amount > 100;` — получишь ошибку. Перепиши двумя способами: через повтор выражения в `WHERE` и через подзапрос. Заодно подумай, какой вариант СУБД выполнит быстрее (ответ: одинаково, планировщик их сведёт к одному).

## Часть 3. Типы данных

### 3.1. Строгая типизация

Главное отличие от SQLite. В SQLite можно положить строку в столбец `INTEGER` — база не возражает. В PostgreSQL нельзя, и это хорошо: ошибка вылезает при записи, а не при подсчёте.

| Тип | Когда | Осторожно |
|---|---|---|
| `integer`, `bigint` | счётчики, идентификаторы | `1/2 = 0` — целочисленное деление |
| `numeric(p,s)` | **деньги** | точный, но медленнее |
| `real`, `double precision` | измерения, доли | накапливает ошибку округления |
| `text`, `varchar(n)` | строки | в Postgres `text` не медленнее `varchar` |
| `boolean` | флаги | значения `true`/`false`/`NULL` |
| `date` | дата без времени | |
| `timestamp` | дата и время без пояса | |
| `timestamptz` | дата и время с поясом | почти всегда правильный выбор |
| `interval` | промежуток | `'7 days'::interval` |
| `jsonb` | полуструктурированное | индексируется, в отличие от `json` |

**Про деньги.** `0.1 + 0.2` в `double precision` даёт `0.30000000000000004`. На одной строке незаметно, на миллионе — расхождение в отчёте, которое невозможно объяснить бухгалтерии. Поэтому суммы в `numeric`. В нашей базе `amount_eur numeric(12,2)`.

**Про целочисленное деление.** Классика:

```sql
SELECT count(*) FILTER (WHERE status='success') / count(*) FROM deposits;  -- 0
SELECT 100.0 * count(*) FILTER (WHERE status='success') / count(*) FROM deposits;  -- 68.5
```

Первый вариант вернёт ноль, потому что оба аргумента целые. Умножение на `100.0` (не на `100`) переводит выражение в числа с точкой. Это ошибка, которую совершают все и по одному разу.

### 3.2. Приведение типов

```sql
SELECT '2026-03-01'::date;
SELECT CAST('42' AS integer);
SELECT amount_eur::text;
SELECT to_char(deposit_ts, 'YYYY-MM') AS month;
SELECT to_date('01.03.2026', 'DD.MM.YYYY');
```

`::` — сокращение PostgreSQL, `CAST` — стандарт SQL. Работают одинаково.

> **Упражнение 3.1.** Посчитай долю успешных депозитов от всех — сначала «в лоб», убедись что получил 0, потом правильно. Затем посчитай ту же долю в разрезе метода оплаты, с округлением до одного знака.

### 3.3. Округление

`round(x)` — до целого. `round(x, 2)` — до двух знаков, но работает только с `numeric`. Для `double precision` нужно привести: `round(x::numeric, 2)`.

Это ещё одно отличие от SQLite, где `round` принимает что угодно.

## Часть 4. Фильтрация

### 4.1. Операторы

```sql
WHERE amount_eur > 100
  AND status = 'success'
  AND method IN ('card', 'applepay')
  AND deposit_ts BETWEEN '2026-03-01' AND '2026-03-31'
  AND user_id NOT IN (562095)
```

Приоритет: `NOT` → `AND` → `OR`. Отсюда классическая ошибка:

```sql
WHERE status = 'success' AND method = 'card' OR method = 'crypto'
```

читается как `(status='success' AND method='card') OR method='crypto'` — то есть все криптодепозиты попадут в выборку независимо от статуса. Скобки не роскошь.

### 4.2. Текст

```sql
WHERE game_name LIKE 'Book%'      -- регистрозависимо
WHERE game_name ILIKE 'book%'     -- регистронезависимо, это Postgres
WHERE utm_source ~ '^partner_'    -- регулярное выражение
WHERE lower(trim(utm_source)) = 'facebook'
```

`ILIKE` и регулярки — то, чего в SQLite нет. Последняя строка — рабочий приём против неявных дубликатов: в нашей базе `utm_source` содержит и `facebook`, и `Facebook`.

### 4.3. NULL

`NULL` — это не ноль и не пустая строка. Это «значение неизвестно». Из чего следует трёхзначная логика:

```sql
NULL = NULL        -- NULL, а не true
NULL <> 'a'        -- NULL, а не true
5 > NULL           -- NULL
NULL AND false     -- false
NULL AND true      -- NULL
NULL OR true       -- true
```

Строка попадает в результат, только если условие дало `true`. `NULL` — не `true`, поэтому не попадает.

Отсюда: `WHERE country <> 'DE'` **не вернёт** игроков с неизвестной страной. Их 103 из 1200, и их молчаливая потеря — самая частая ошибка в отчётах.

Правильно: `WHERE country IS DISTINCT FROM 'DE'` — это оператор PostgreSQL, который сравнивает `NULL` как обычное значение. Или явно: `WHERE country <> 'DE' OR country IS NULL`.

**Ловушка `NOT IN`.** Если подзапрос вернёт хоть один `NULL`, `NOT IN` вернёт пустой результат всегда:

```sql
SELECT * FROM users WHERE user_id NOT IN (SELECT user_id FROM some_table);
-- если в some_table.user_id есть NULL — ноль строк, без предупреждения
```

Потому что `x NOT IN (1, 2, NULL)` разворачивается в `x<>1 AND x<>2 AND x<>NULL`, а последнее — `NULL`. Используй `NOT EXISTS` или анти-джойн.

### 4.4. Работа с NULL

```sql
COALESCE(country, 'unknown')      -- первое не-NULL значение
NULLIF(a, b)                      -- NULL, если a = b (защита от деления на ноль)
country IS NULL / IS NOT NULL
```

`NULLIF` в знаменателе — обязательная привычка:

```sql
round(100.0 * ftd / NULLIF(regs, 0), 1)
```

Без этого запрос упадёт на канале, где не было ни одной регистрации.

> **Упражнение 4.1.** Посчитай число игроков по странам двумя запросами: с `WHERE country <> 'DE'` и с `WHERE country IS DISTINCT FROM 'DE'`. Объясни разницу в общем количестве. Потом посчитай общее число визитов по `utm_source`, сначала как есть, потом с приведением регистра — сравни строки `facebook`.

## Часть 5. Агрегация

### 5.1. Функции

```sql
count(*)                      -- строки
count(col)                    -- строки, где col не NULL
count(DISTINCT col)           -- уникальные не-NULL значения
sum(col), avg(col), min(col), max(col)
```

Разница между `count(*)` и `count(col)` — это способ узнать число пропусков, не считая их отдельно:

```sql
SELECT count(*) - count(country) AS missing_country FROM users;
```

`avg` и `sum` игнорируют `NULL`. Это значит, что `avg` считает среднее по непустым значениям, а не по всем строкам. Иногда это то, что нужно, иногда нет — но решение должно быть осознанным.

### 5.2. FILTER

Постгресовый синтаксис, которого нет в SQLite и который сильно чище, чем `SUM(CASE WHEN)`:

```sql
SELECT
  count(*)                                   AS all_deposits,
  count(*) FILTER (WHERE status='success')   AS successful,
  sum(amount_eur) FILTER (WHERE status='success' AND dep_number=1) AS ftd_volume
FROM deposits;
```

То же самое через `CASE`:

```sql
  sum(CASE WHEN status='success' THEN 1 ELSE 0 END) AS successful
```

`FILTER` короче, читается лучше и работает с любой агрегатной функцией. Привыкай к нему — это одно из главных удобств, которое даёт переход на Postgres.

> **Упражнение 5.1.** Одним запросом посчитай по каждому методу оплаты: всего попыток, успешных, неуспешных, сумму успешных и процент успеха. Используй `FILTER`, без `CASE`.

## Часть 6. Группировка и сортировка

### 6.1. Зернистость

Главный вопрос перед любым `GROUP BY`: **что означает одна строка результата?**

`GROUP BY country` — строка это страна. `GROUP BY country, device` — строка это пара страна-устройство. Если в `SELECT` попало поле, которого нет ни в `GROUP BY`, ни под агрегатом, PostgreSQL выдаст ошибку. SQLite в этом случае молча вернёт произвольное значение — и это одна из причин, почему на Postgres ошибок в отчётах меньше.

### 6.2. GROUP BY и HAVING

```sql
SELECT method, count(*) AS n, round(avg(amount_eur), 2) AS avg_amount
FROM deposits
WHERE status = 'success'          -- фильтр строк, до группировки
GROUP BY method
HAVING count(*) >= 50             -- фильтр групп, после
ORDER BY n DESC, method;
```

Правило выбора: если условие можно проверить на одной строке — это `WHERE`. Если для проверки нужна вся группа — `HAVING`. `WHERE` дешевле, потому что отсекает строки раньше.

Можно группировать по номеру столбца: `GROUP BY 1`. Удобно при разведке, плохо в коде, который кто-то будет читать.

### 6.3. Сортировка

```sql
ORDER BY turnover DESC, country ASC
ORDER BY country NULLS FIRST
LIMIT 10 OFFSET 20
```

В PostgreSQL `NULL` по умолчанию сортируется **последним** при `ASC` и **первым** при `DESC`. В SQLite — наоборот. Если переносишь запрос и результат разошёлся на одну строку, смотри сюда.

**Важно про детерминированность.** `ORDER BY turnover DESC LIMIT 5` при одинаковых значениях `turnover` может вернуть разные строки от запуска к запуску: порядок среди равных не определён. Всегда добавляй тай-брейк — второй столбец сортировки, гарантирующий уникальность. Это не педантизм: отчёт, который «иногда показывает другого мастера на пятом месте», отлаживается мучительно.

> **Упражнение 6.1.** Топ-10 игр по обороту. Сначала без тай-брейка, потом с ним. Потом то же, но только для игр, где было не меньше 200 ставок.
