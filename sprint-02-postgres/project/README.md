# Проект спринта 2. Стриминговый сервис «Поток»

## Постановка от заказчика

Продуктовая команда музыкального сервиса «Поток» готовит квартальный обзор для инвесторов и просит аналитика подготовить фактуру:

> «Нужна общая картина по прослушиваниям: кто слушает, что слушают, откуда приходят прослушивания, как это связано с тарифами. И отдельно — что там с бесплатным тарифом, он вообще во что-то конвертируется?»

Как и в прошлом спринте, это не задача, а направление. Первый шаг — превратить в список вопросов.

## Данные

Схема `stream` в базе курса. Поднять:

```bash
make stream
```

| Таблица | Строк | Зернистость |
|---|---|---|
| `artists` | 400 | исполнитель |
| `tracks` | 6 000 | трек |
| `users` | 8 000 | слушатель |
| `subscriptions` | 3 350 | подписка |
| `listens` | 1 155 386 | прослушивание |
| `playlists` | 9 448 | плейлист |
| `playlist_tracks` | 223 686 | трек в плейлисте |

Период: июль 2025 — июнь 2026.

Что стоит знать заранее:

- `users.plan` — текущий тариф, `free` / `individual` / `duo` / `family`. У бесплатных строк в `subscriptions` нет.
- `listens.ms_played` — сколько миллисекунд реально проиграно. Прослушивание считается **засчитанным**, если проиграно не меньше 30 секунд.
- `subscriptions.ended_at = NULL` означает активную подписку.
- `playlist_tracks` не имеет первичного ключа.
- В данных есть дефекты. Найти их — часть задачи.

## Что сделать

Написать SQL-запросы, отвечающие на вопросы. Только то, что проходили: `SELECT`, `WHERE`, агрегаты, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`, `FILTER`, работа с `NULL` и типами. Джойны и CTE будут в следующем спринте — здесь обойдись без них там, где возможно, и обозначь, где без джойна не выходит.

**Блок 1. Осмотреться.**
1. Границы периода: первое и последнее прослушивание.
2. Размер каждой таблицы.
3. Доля пропусков по каждому столбцу, где они возможны.
4. Есть ли аномалии в `ms_played`: сколько строк с нулём, сколько с отрицательным, сколько подозрительно больших.

**Блок 2. Аудитория.**
5. Распределение пользователей по тарифам и возрастным группам.
6. Топ-10 стран по числу пользователей. Пользователей без страны не потерять — показать отдельной строкой.
7. Динамика регистраций по месяцам.

**Блок 3. Прослушивания.**
8. Число засчитанных прослушиваний по месяцам.
9. Распределение по устройствам и источникам запуска.
10. Доля дослушанных до конца — по устройствам. Сформулируй сам, что считать «до конца», и обоснуй порог.
11. Средняя и медианная длительность прослушивания. Объясни разницу между ними.

**Блок 4. Контент.**
12. Топ-20 треков по числу засчитанных прослушиваний.
13. Топ-10 жанров по прослушиваниям. Проверь, нет ли в жанрах неявных дубликатов.
14. Сколько треков не прослушали ни разу.

**Блок 5. Деньги и тарифы.**
15. Активные подписки по тарифам, помесячная выручка.
16. Доля оттока: сколько подписок закончилось и не возобновилось.
17. Отличается ли интенсивность прослушиваний у платных и бесплатных — в прослушиваниях на пользователя в месяц.

**Блок 6. Ответ на вопрос заказчика.**
18. Что можно сказать про бесплатный тариф на этих данных — и, что важнее, **чего сказать нельзя** и почему. Данных для полноценного ответа про конверсию free → paid здесь не хватает. Сформулируй, какие данные нужно было бы собрать.

## Что сдать

1. `solution.sql` — все запросы, пронумерованные, с комментарием-вопросом перед каждым.
2. `README.md` — отчёт: постановка, принятые определения, результаты по блокам, выводы. Для человека, который SQL не читает.
3. Список найденных дефектов данных с оценкой влияния на расчёты.

## Критерии приёмки

Обязательные:

- [ ] Есть блок «Определения»: что считаем засчитанным прослушиванием, активной подпиской, оттоком. До расчётов.
- [ ] Осмотр данных проведён до содержательных запросов, результаты зафиксированы.
- [ ] Найдены минимум 3 дефекта данных, по каждому — оценка влияния и решение.
- [ ] Пользователи с неизвестной страной не потеряны молча.
- [ ] Доли считаются без целочисленного деления, знаменатель защищён от нуля.
- [ ] Везде, где есть `LIMIT`, сортировка детерминирована — есть тай-брейк.
- [ ] Посчитаны и среднее, и медиана там, где распределение с хвостом; разница объяснена словами.
- [ ] Запросы отформатированы единообразно, читаются сверху вниз.
- [ ] Пункт 18 отвечает честно: сказано, чего данные не позволяют утверждать.
- [ ] Отчёт понятен без чтения SQL.

Желательные:

- [ ] `FILTER` вместо `SUM(CASE WHEN)`.
- [ ] Есть хотя бы один санити-чек: сумма по разрезам сходится с общим итогом.
- [ ] Найден дефект, о котором в этом ТЗ не сказано.

## Ловушка

Один из вопросов сформулирован так, что на него нельзя ответить корректно имеющимися данными. Если ты ответил на все 18 пунктов уверенно и без оговорок — перечитай ещё раз. Умение сказать «этих данных недостаточно» ценится выше, чем умение выдать число.
