# Проект спринта 10. Вероятностные расчёты и смена поддержки

## Что это за задание

Проект без ревью-кейса: здесь важна правильность расчётов, а не оформление выводов. Зато каждый ответ проверяется двумя способами — аналитически и симуляцией. Расхождение означает ошибку в одном из двух.

Данные — база курса, схема `casino`. Забирать их в Python можно двумя путями: считать агрегаты в SQL и переносить числа, или подключиться через `sqlalchemy` и работать с датафреймами. Второй способ предпочтительнее — заодно потренируешь связку.


### Часть 1. Конверсия как случайная величина

5. Сколько наблюдений нужно, чтобы оценить конверсию с точностью ±2 процентных пункта при 95% уровне доверия? А с точностью ±1 пп?

### Часть 2. Цепочка условных вероятностей

### Часть 4. Планирование смены поддержки

В базе 520 обращений в поддержку за 290 дней.

15. Вероятность получить не менее 3, 4, 5, 6 обращений в день.
16. Сколько обращений в день надо быть готовым обработать, чтобы справляться в 95% дней?
17. Продукт планирует рост в 5, 10 и 20 раз. Для каждого сценария: среднее число обращений, 95-й и 99-й перцентиль.
18. Один оператор обрабатывает 12 обращений за смену. Сколько операторов держать при каждом сценарии роста, если цель — справляться в 95% дней? А в 99%?
19. Объясни, почему планирование по среднему приводит к перегрузкам примерно в половине смен.

## Про последний желательный пункт

Он самый интересный. Пуассон предполагает, что события независимы и интенсивность постоянна. В реальности ни то, ни другое не выполняется: обращения зависят от активности игроков, а активность зависит от дня недели.

Если наблюдаемая дисперсия числа обращений заметно больше среднего (для Пуассона они равны), значит модель не подходит и планировать по ней нельзя — нужно разделять по дням недели или брать отрицательное биномиальное распределение.

Проверить это — одна строка кода. Сделать вывод из результата — то, за что аналитику платят.
