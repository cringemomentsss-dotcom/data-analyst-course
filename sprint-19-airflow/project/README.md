# Проект спринта 19. DAG для пайплайна

**С ревью.** Сдаёшь в `solutions/`, я проверяю по критериям приёмки.

---

## Постановка

Пайплайн из спринта 18 работает. Запускается он тем, что ты открываешь терминал и набираешь `spark-submit`.

Это не пайплайн, это скрипт. Пайплайном он станет, когда: пойдёт по расписанию; дождётся появления данных, а не упадёт на их отсутствии; переживёт сетевой сбой; сообщит, если сломался; и позволит пересчитать любой прошлый день одной командой.

**Задача:** обернуть его в DAG, который делает всё перечисленное.

## Окружение

```bash
make air     # поднять Airflow, UI на localhost:8080 (analyst / analyst)
make air-cli CMD='dags list'
make air-cli CMD='tasks test мой_dag моя_задача 2026-06-05'
```

DAG-и кладутся в [`dags/`](dags/) — папка смонтирована в контейнер.

**Про память.** Airflow съедает около 1,4 ГБ, ClickHouse ещё полгигабайта, MinIO — сто с лишним. При типовых 3,8 ГБ на весь Docker одновременный запуск Airflow, Spark-задачи и ClickHouse — на грани. Если что-то падает с кодом 137, это OOM: погаси лишнее через `make module6-down` и подними только нужное, либо добавь Docker памяти в настройках.

Режим Airflow здесь — `standalone`: SQLite и SequentialExecutor, задачи идут по одной. Для учёбы этого достаточно, для прода — нет, и в отчёте это надо назвать.

## Что сдать

### 1. DAG

`dags/pipeline_dag.py`. Что он делает:

1. **Дожидается данных** — сенсор на появление партиции в MinIO.
2. **Запускает обработку** Spark за конкретную логическую дату.
3. **Загружает витрину** в ClickHouse.
4. **Проверяет качество** — тесты на данные по образцу спринта 15.
5. **Сообщает об ошибке.**

Требования:

- **логическая дата — параметр обработки.** `{{ ds }}`, а не `datetime.now()`. Перезапуск за прошлый день должен обработать прошлый день;
- **retry с экспоненциальной выдержкой** и потолком;
- **сенсор с таймаутом**. Без таймаута — незачёт, это не придирка: файл, который никогда не приедет, случается гарантированно;
- **секреты в Connections**, в коде только идентификаторы соединений;
- **уведомление об ошибке** — `on_failure_callback` или `email_on_failure`. Пусть пишет в лог, если почты нет, но механизм должен быть;
- **зависимости объявлены явно.** Задача, читающая то, что пишет другая, обязана от неё зависеть, даже если «и так по порядку идёт».

Проверить конфиг можно функцией `dag_review` из [тренажёра](../trenazher/zadachi.py) — она собрана ровно из этих требований.

### 2. Доказательство идемпотентности

`idempotent.md`. Запусти DAG за одну и ту же дату дважды и покажи, что данные не изменились: числа до и после.

Не «DAG идемпотентен», а таблица из двух прогонов.

### 3. Backfill

`backfill.md`. Пересчитай период задним числом:

```bash
make air-cli CMD='dags backfill -s 2026-06-05 -e 2026-06-08 pipeline_dag'
```

Покажи, что отработало, сколько запусков создалось и что стало с данными. Если что-то пошло не так — это тоже результат, опиши.

### 4. Разбор графа

`graph.md`:

- схема DAG: задачи и зависимости;
- топологические уровни: что могло бы идти параллельно (и почему в SequentialExecutor не идёт);
- критический путь и его длительность;
- проверка на скрытые зависимости — `find_hidden_deps` из тренажёра.

### 5. Записка про эксплуатацию

`ekspluataciya.md`, страница:

- что делать, когда DAG упал ночью: куда смотреть, в каком порядке;
- какие задачи безопасно перезапускать, какие нет;
- что сломается, если источник данных опоздает на шесть часов;
- чего не хватает этой сборке до продовой.

## Ловушки

**1. `catchup` по умолчанию включён.** Поставил `start_date` полгода назад, включил DAG — и Airflow немедленно создал 161 запуск, которые дружно пошли в один источник. Ставь `catchup=False` и включай осознанно.

**2. Логическая дата — не дата запуска.** Запуск за первое июня стартует второго. Первое время это сбивает всех: в UI написано «первое», а лог датирован вторым. Причина разумная — данные за первое июня не полны, пока оно не кончилось.

**3. Имя параметра задачи может совпасть с ключом контекста.** TaskFlow подставляет в параметр `ds` значение по умолчанию, и следующий за ним обязательный аргумент ломает подпись:

```
ValueError: ... which isn't valid: non-default argument follows default argument
```

Лечится двумя способами: либо давать `ds` значение по умолчанию и ставить его последним, либо называть параметры так, чтобы они не совпадали с ключами контекста. В [`dags/demo_taskflow.py`](dags/demo_taskflow.py) показаны оба.

**4. Сенсор в режиме `poke` держит слот.** В SequentialExecutor слот один. Сенсор в `poke`, ждущий полчаса, — это остановленный на полчаса пайплайн. Для долгого ожидания `mode="reschedule"`.

**5. `depends_on_past` вместе с `catchup`.** Один сбой в прошлом останавливает всю цепочку, и разгребать её приходится вручную.

**6. Незаполненный макрос не ошибка.** `{{ ds }}` без контекста подставится пустой строкой, путь `s3://raw/dt=/` вернёт ноль строк, DAG отработает «успешно» и запишет пустую витрину. Проверяй, что подставилось.

**7. Тяжёлый код на уровне модуля.** Всё, что написано в файле DAG вне функций задач, выполняется при **каждом** разборе файла — раз в тридцать секунд. Запрос к базе на верхнем уровне DAG-файла — это запрос к базе раз в тридцать секунд, круглосуточно.

## Критерии приёмки

**Обязательное**

- [ ] DAG подхватывается Airflow без ошибок разбора.
- [ ] Логическая дата используется как параметр обработки; `datetime.now()` в логике нет.
- [ ] Идемпотентность показана двумя прогонами за одну дату, с числами.
- [ ] Зависимости объявлены явно; скрытых нет, проверено.
- [ ] Секреты в Connections или Variables; в коде DAG паролей нет.
- [ ] Настроены retry с выдержкой; названо, почему выбрано именно столько попыток.
- [ ] Есть сенсор, и у него есть таймаут; выбран режим `poke` или `reschedule` с обоснованием.
- [ ] Настроено уведомление об ошибке.
- [ ] `catchup` задан явно, решение обосновано.
- [ ] Backfill за прошлый период выполнен, результат описан.
- [ ] Разобран граф: уровни, критический путь.
- [ ] Записка про эксплуатацию: что делать при ночном падении.
- [ ] Названо, чего этой сборке не хватает до продовой.

**Желательное**

- [ ] Ветвление: пропускать обработку, если данных за день нет.
- [ ] SLA и разбор, что делать при его нарушении.
- [ ] Пул, ограничивающий число одновременных обращений к ClickHouse.
- [ ] Тесты на данные вынесены в отдельные задачи и валят DAG при провале.
- [ ] Отдельный DAG для перезаливки, независимый от основного.
- [ ] Датасеты (`Dataset`) вместо расписания: запуск по готовности данных.

## Как я буду ревьюить

1. **Логическая дата.** Используется или подменена на `now()`. Второе — сразу на доработку: это делает пайплайн невоспроизводимым.
2. **Идемпотентность.** Показана прогонами или заявлена словами.
3. **Сенсор.** Есть таймаут или нет.
4. **Секреты.** В коде или в Connections.
5. **Скрытые зависимости.** Проверены или нет.
6. **Записка.** Понятно ли из неё, что делать в три часа ночи.
