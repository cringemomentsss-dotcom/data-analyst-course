# Спринт 4. Оконные функции, описательная статистика, ad hoc

**1 неделя.** Последний SQL-спринт модуля и самый важный. Оконные функции — водораздел: до них аналитик умеет считать агрегаты, после — умеет считать динамику, ранги, доли, накопления и всё, что требует смотреть на строку в контексте остальных.

Плюс здесь появляется первый слой статистики: среднее против медианы, разброс, перцентили. Не как теория, а как ответ на вопрос «какую цифру нести в отчёт».

**На выходе:** проект на данных онлайн-игры, где ты сам формулируешь вопросы.

Тренажёр: [trenazher/zadachi.sql](trenazher/zadachi.sql), 20 задач.

## Часть 1. Как изучать незнакомую базу

Начинаем этим, потому что в проекте спринта база новая, и это ровно то, что делают в первую неделю на новой работе.

### 1.1. Порядок

**Шаг 1. Что вообще есть.** Список таблиц с числом строк — сразу видно, где факты (миллионы строк), а где справочники (десятки).

**Шаг 2. Из чего состоит.** Столбцы и типы. Обрати вним, что `NOT NULL`, а что нет: nullable-столбец — это заявление «здесь бывает пусто».

**Шаг 3. Как связано.** Внешние ключи. Если их нет — связи всё равно есть, но не гарантированы, и это первое, что надо проверить.

**Шаг 4. Границы периода.** `min` и `max` по всем датам. Часто выясняется, что таблицы покрывают разные периоды, и пересечение короче, чем кажется.

**Шаг 5. Уникальность.** Проверить, что первичный ключ действительно уникален, а смысловой ключ — тоже:

```sql
SELECT player_id, level, count(*) FROM levels
GROUP BY 1,2 HAVING count(*) > 1;
```

**Шаг 6. Доля пропусков по столбцам.**

```sql
SELECT count(*) AS rows,
       count(*) - count(country)  AS country_null,
       count(*) - count(promo_code) AS promo_null
FROM purchases;
```

**Шаг 7. Распределения категорий.** Для каждого текстового столбца — `GROUP BY` с количеством. Здесь вылезают неявные дубликаты и неожиданные значения.

**Шаг 8. Распределения чисел.** `min`, `max`, перцентили. Здесь вылезают отрицательные суммы, нули вместо `NULL` и значения-заглушки вроде `-1` и `9999`.

### 1.2. Что записывать

Заведи файл `explore.sql` и складывай туда все запросы разведки с ответами в комментариях. Через неделю ты не вспомнишь, сколько было пропусков, а в отчёте это придётся указать.

> **Упражнение:** прогони все восемь шагов на схеме `game` (`make game`) до того, как начнёшь проект. Это займёт час и сэкономит день.

## Часть 2. Оконные функции: основы

### 2.1. Чем отличаются от GROUP BY

`GROUP BY` схлопывает строки: было 51 087 ставок, стало 4 строки по категориям. Детали потеряны.

Оконная функция считает агрегат **и оставляет все строки на месте**:

```sql
SELECT user_id, amount_eur,
       sum(amount_eur) OVER (PARTITION BY user_id) AS user_total
FROM deposits;
```

Каждая строка знает и свою сумму, и сумму по игроку. Это невозможно одним `GROUP BY` — пришлось бы делать подзапрос и джойн.

### 2.2. Синтаксис

```sql
функция(аргументы) OVER (
    PARTITION BY столбцы     -- разбить на независимые окна
    ORDER BY столбцы         -- порядок внутри окна
    рамка                    -- какие строки окна участвуют
)
```

Все три части необязательны. `OVER ()` без ничего — окно во всю таблицу:

```sql
-- доля каждой страны от общего числа игроков
SELECT country, count(*) AS users,
       round(100.0 * count(*) / sum(count(*)) OVER (), 1) AS share_pct
FROM users GROUP BY country;
```

Обрати внимание на `sum(count(*)) OVER ()` — агрегат от агрегата. Это законно и очень полезно: оконные функции выполняются **после** `GROUP BY`, поэтому видят уже сгруппированные строки. Понимание этого места экономит массу подзапросов.

### 2.3. Где нельзя

Оконные функции считаются между `SELECT` и `ORDER BY`, а значит:

- в `WHERE` по ним фильтровать нельзя;
- в `GROUP BY` и `HAVING` — тоже нельзя.

Чтобы отфильтровать по результату окна, нужен подзапрос или CTE:

```sql
SELECT * FROM (
  SELECT user_id, amount_eur,
         row_number() OVER (PARTITION BY user_id ORDER BY deposit_ts) AS rn
  FROM deposits
) t WHERE rn = 1;
```

В некоторых СУБД (ClickHouse, Snowflake, BigQuery) для этого есть `QUALIFY`. В PostgreSQL — нет, и это самая частая причина обёртки в подзапрос.

### 2.4. Агрегирующие в окне

`sum`, `count`, `avg`, `min`, `max` — все работают с `OVER`.

```sql
-- доля игры внутри своей категории
SELECT g.category, g.game_name, sum(b.stake_eur) AS turnover,
       round(100.0 * sum(b.stake_eur)
             / sum(sum(b.stake_eur)) OVER (PARTITION BY g.category), 1) AS share_in_cat
FROM bets b JOIN games g USING (game_id)
GROUP BY g.category, g.game_name;
```

### 2.5. Ранжирующие

```sql
row_number()   -- 1,2,3,4  — уникальный номер, равные значения различаются произвольно
rank()         -- 1,2,2,4  — равным одинаковый ранг, следующий с пропуском
dense_rank()   -- 1,2,2,3  — равным одинаковый ранг, без пропуска
ntile(n)       -- разбить на n примерно равных групп
percent_rank() -- относительное положение от 0 до 1
```

Выбор:

- **`row_number`** — когда нужно ровно по одной строке (дедупликация, «первый платёж»). Обязательно с тай-брейком в `ORDER BY`, иначе результат недетерминирован.
- **`rank`** — когда важно, что двое разделили второе место.
- **`dense_rank`** — когда нужны последовательные номера уровней.
- **`ntile`** — децили и квартили: сегментация плательщиков по сумме.
- **`percent_rank`** — «топ 10% по обороту» без знания абсолютных границ.

**Дедупликация через `row_number` — самый частый производственный приём:**

```sql
SELECT * FROM (
  SELECT *, row_number() OVER (PARTITION BY visitor_id, event_ts, event_name
                               ORDER BY page_event_id) AS rn
  FROM page_events
) t WHERE rn = 1;
```

Ключ партиционирования — то, что определяет «одну и ту же сущность». `ORDER BY` решает, какую из копий оставить.

**Топ-N внутри группы:**

```sql
SELECT * FROM (
  SELECT category, game_name, turnover,
         row_number() OVER (PARTITION BY category ORDER BY turnover DESC) AS rn
  FROM ...
) t WHERE rn <= 3;
```

## Часть 3. Смещения

### 3.1. LAG и LEAD

```sql
lag(x)       -- значение x из предыдущей строки окна
lead(x)      -- из следующей
lag(x, 2)    -- на две строки назад
lag(x, 1, 0) -- на одну назад, а если строки нет — 0 вместо NULL
```

Главное применение — динамика:

```sql
WITH w AS (
  SELECT date_trunc('week', bet_ts)::date AS week_start, sum(stake_eur) AS turnover
  FROM bets GROUP BY 1
)
SELECT week_start, turnover,
       round(100.0 * (turnover - lag(turnover) OVER (ORDER BY week_start))
             / lag(turnover) OVER (ORDER BY week_start), 1) AS wow_pct
FROM w;
```

Второе применение — интервалы между событиями одного объекта:

```sql
SELECT user_id, deposit_ts,
       deposit_ts - lag(deposit_ts) OVER (PARTITION BY user_id ORDER BY deposit_ts) AS gap
FROM deposits WHERE status = 'success';
```

Так считают время между покупками, между сессиями, между обращениями в поддержку — то есть частоту в модели RFM.

### 3.2. FIRST_VALUE и LAST_VALUE

```sql
first_value(game_id) OVER (PARTITION BY user_id ORDER BY bet_ts)
```

С `first_value` всё интуитивно. С `last_value` — ловушка, на которой спотыкаются все.

**По умолчанию рамка окна — `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.** То есть «от начала окна до текущей строки». Поэтому `last_value` вернёт... текущую строку, а не последнюю в окне.

Правильно:

```sql
last_value(game_id) OVER (
  PARTITION BY user_id ORDER BY bet_ts, bet_id
  ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
)
```

Это не каприз синтаксиса — это следствие того, что рамка по умолчанию задумана под нарастающие итоги.

> **Упражнения:** t4.6, t4.7, t4.10.

## Часть 4. Рамки окна

### 4.1. ROWS против RANGE

```sql
ROWS  BETWEEN 6 PRECEDING AND CURRENT ROW    -- 7 физических строк
RANGE BETWEEN '6 days' PRECEDING AND CURRENT ROW  -- логический интервал значений
```

`ROWS` считает строки. `RANGE` считает значения `ORDER BY`.

Разница видна на пропусках. Если в данных нет 14 февраля, то `ROWS 6 PRECEDING` возьмёт семь имеющихся строк — то есть заглянет на восемь календарных дней назад. `RANGE '6 days' PRECEDING` возьмёт ровно календарное окно.

Для скользящих средних по времени правильнее `RANGE`. Но `RANGE` с интервалами медленнее и поддерживается только с PostgreSQL 11. На практике чаще строят полный календарь через `generate_series` (спринт 3) и потом используют `ROWS` — так и быстрее, и понятнее.

### 4.2. Нарастающий итог

```sql
sum(daily) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
```

Рамку можно не писать — она такова по умолчанию при наличии `ORDER BY`. Но писать полезно: читающий сразу видит замысел, а не догадывается.

### 4.3. Скользящее среднее

```sql
avg(turnover) OVER (ORDER BY d ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
```

Зачем нужно: суточные метрики шумят из-за недельной сезонности — по выходным всегда больше. Скользящее среднее за 7 дней убирает сезонность и показывает тренд.

Важно: первые шесть точек считаются по неполному окну, поэтому начало ряда искажено. В отчёте эти точки либо отбрасывают, либо помечают.

### 4.4. Острова и промежутки

Класс задач: «максимальная серия дней подряд», «непрерывные периоды активности», «сколько раз абонент возвращался».

Приём с нумерацией:

```sql
WITH d AS (
  SELECT DISTINCT user_id, session_date FROM sessions
), grp AS (
  SELECT user_id, session_date,
         session_date - (row_number() OVER (PARTITION BY user_id
                                            ORDER BY session_date))::int AS island
  FROM d
)
SELECT user_id, island, count(*) AS streak_len, min(session_date), max(session_date)
FROM grp GROUP BY user_id, island;
```

Почему работает: если даты идут подряд, то `дата минус номер строки` даёт одну и ту же константу для всей серии. Как только появляется пропуск, константа меняется — начинается новый «остров». Дальше обычный `GROUP BY` по этой константе.

Приём стоит запомнить целиком: он решает весь класс задач и регулярно встречается на собеседованиях.

> **Упражнения:** t4.8, t4.9, t4.11, t4.19.

## Часть 5. Описательная статистика

### 5.1. Две группы мер

**Центр** — вокруг чего сгруппированы данные: среднее, медиана, мода.
**Разброс** — насколько разбросаны: размах, дисперсия, стандартное отклонение, IQR.

Сообщать одну без другой почти всегда бессмысленно. «Средний чек 52 евро» ничего не говорит, если не знать, что медиана — 30, а девяностый перцентиль — 115.

### 5.2. Когда среднее врёт

В нашей базе размер успешного депозита:

| p25 | медиана | среднее | p75 | p90 |
|---|---|---|---|---|
| 15,51 | 29,92 | 52,02 | 61,14 | 114,96 |

Среднее почти вдвое больше медианы. Это признак **правого хвоста**: небольшое число крупных депозитов тянет среднее вверх. Половина игроков кладёт меньше 30 евро, но «средний игрок» по отчёту кладёт 52.

Такое распределение — норма для всего, что связано с деньгами и временем: чеки, LTV, длительность сессий, время до конверсии. Все они логнормальны, а не нормальны.

Практическое правило:

- распределение симметричное → **среднее**;
- есть хвост → **медиана** как основная цифра, среднее как дополнение;
- нужен полный портрет → **перцентили** p25/p50/p75/p90.

И отдельно: **сумма всегда считается суммой**, а не средним × количеством. Выручка — это `sum`, и хвост здесь не помеха, а суть.

### 5.3. Перцентили в PostgreSQL

Это то, чего в SQLite не было и что приходилось изобретать вручную:

```sql
SELECT percentile_cont(0.5) WITHIN GROUP (ORDER BY amount_eur) AS median,
       percentile_cont(0.9) WITHIN GROUP (ORDER BY amount_eur) AS p90,
       percentile_disc(0.5) WITHIN GROUP (ORDER BY amount_eur) AS median_disc
FROM deposits WHERE status = 'success';
```

`percentile_cont` интерполирует между соседними значениями — годится для чисел. `percentile_disc` возвращает реально существующее значение из данных — годится, когда интерполяция бессмысленна (например, для дат или порядковых шкал).

`WITHIN GROUP` — обязательная часть синтаксиса упорядоченных агрегатов. Выглядит непривычно, но пишется всегда одинаково.

### 5.4. Разброс

```sql
max(x) - min(x)                                  -- размах, чувствителен к выбросам
var_samp(x), stddev_samp(x)                      -- выборочные (обычно нужны эти)
var_pop(x),  stddev_pop(x)                       -- по генеральной совокупности
percentile_cont(0.75) ... - percentile_cont(0.25) ...   -- IQR
```

Стандартное отклонение чувствительно к выбросам ровно так же, как среднее. IQR — нет: он описывает середину распределения. Для данных с хвостом сообщай IQR.

Про `samp` и `pop`: разница в знаменателе (`n-1` против `n`), на больших выборках несущественна. По умолчанию бери `samp` — почти всегда у тебя выборка, а не вся совокупность. Подробнее — в модуле 4.

### 5.5. Мода

```sql
SELECT mode() WITHIN GROUP (ORDER BY method) FROM deposits WHERE status='success';
```

Единственная мера центра, работающая для категорий: у метода оплаты нет среднего.

### 5.6. Выбросы

Два формальных правила:

- **1,5 × IQR**: выброс — всё, что ниже `p25 - 1.5*IQR` или выше `p75 + 1.5*IQR`. Работает на любых распределениях.
- **3 сигмы**: выброс — всё, что дальше трёх стандартных отклонений от среднего. Корректно только для нормального распределения, а деньги ненормальны — так что для чеков этот критерий даст ерунду.

И главное: **выброс не значит ошибка.** Депозит на 5000 евро от кита — это выброс и это самая ценная строка в таблице. Удалять его нельзя. Ошибка — это депозит на −100 или на 999 999. Различать одно от другого умеет только человек, знающий предметную область.

> **Упражнения:** t4.12–t4.17, t4.20.

## Часть 6. Ad hoc задачи

### 6.1. Что это и почему это главное

Ad hoc — разовый вопрос, на который надо ответить сейчас. Не дашборд, не регулярный отчёт, а «слушай, а сколько у нас игроков из Германии платят больше 100 евро в месяц?».

Это большая часть работы аналитика. И именно здесь чаще всего дают неверные ответы, потому что вопрос кажется простым и на него отвечают сразу, не уточнив.

### 6.2. Алгоритм

**1. Уточнить вопрос.** Три вещи, которые надо выяснить всегда:
   - **Определения.** «Активный игрок» — это кто? Сделал ставку, зашёл, или сделал депозит?
   - **Период.** Календарный месяц, последние 30 дней, или с начала года?
   - **Зачем.** Под какое решение нужна цифра. Это меняет ответ: под премию менеджеру нужна одна метрика, под решение о закрытии канала — другая.

**2. Проверить, что данные есть.** До того, как писать запрос. Если разметки нет — честный ответ «эти данные не собираются», а не «конверсия 0%».

**3. Декомпозировать.** Разбить на шаги, каждый шаг — CTE. Не пытаться написать всё одним запросом.

**4. Посчитать.**

**5. Проверить себя.** Обязательный шаг, а не бонус. Три приёма:
   - **Санити-чек**: сумма по разрезам равна общему итогу.
   - **Порядок величины**: 40% конверсии в депозит — это правдоподобно? А 0,04%?
   - **Другой путь**: посчитать иначе и сравнить. Если два способа дали разное — один из них неверен, и надо понять какой.

**6. Ответить.** Цифра, метод одной фразой, оговорки. Не таблица на 200 строк.

### 6.3. Как отвечать, когда данных нет

Худший ответ — посчитать по имеющимся данным и не сказать, что они неполные. Так рождаются решения на основе мусора.

Правильно: «Ответить нельзя, потому что событие X не размечено с июня. Могу посчитать по прокси-метрике Y, но она завышает результат примерно на столько-то, потому что не отличает A от B. Чтобы ответить точно, нужно добавить в трекинг вот это.»

Такой ответ выглядит менее уверенно и стоит гораздо дороже.

### 6.4. Декомпозиция: пример

Вопрос: «Наши киты — они приходят из какого канала?»

Разбор:
- «Киты» — кто? Топ-10% по сумме депозитов? Топ-1%? Абсолютный порог? → **договориться**, взять топ-10% по LTV.
- «Приходят из канала» — канал регистрации из `users.source`. Но у 22 игроков он пуст → **показать отдельной строкой**, не прятать.
- Сравнивать с чем? Доля канала среди китов сама по себе бесполезна — нужна доля канала среди всех, чтобы увидеть перевес.

Запрос:

```sql
WITH ltv AS (
  SELECT user_id, sum(amount_eur) AS dep
  FROM deposits WHERE status='success' GROUP BY user_id
), ranked AS (
  SELECT user_id, dep, percent_rank() OVER (ORDER BY dep DESC) AS pr FROM ltv
), whales AS (
  SELECT user_id FROM ranked WHERE pr < 0.10
)
SELECT u.source,
       count(*) FILTER (WHERE w.user_id IS NOT NULL) AS whales,
       count(*) AS all_users,
       round(100.0 * count(*) FILTER (WHERE w.user_id IS NOT NULL)
             / nullif(count(*), 0), 1) AS whale_rate_pct
FROM users u LEFT JOIN whales w ON w.user_id = u.user_id
GROUP BY u.source ORDER BY whale_rate_pct DESC NULLS LAST;
```

Последний столбец — то, что отвечает на вопрос. Доля китов внутри канала, а не доля канала внутри китов. Разница между этими двумя цифрами — типичный источник неверных выводов о каналах.

> **Упражнение:** t4.18.

## Литература

- [PostgreSQL: Window Functions Tutorial](https://postgrespro.ru/docs/postgresql/17/tutorial-window) и раздел 3.5 — начать отсюда.
- [PostgreSQL: Window Function Calls](https://postgrespro.ru/docs/postgresql/17/sql-expressions#SYNTAX-WINDOW-FUNCTIONS) — точное описание рамок окна.
- [Aggregate Functions: percentile_cont, mode](https://postgrespro.ru/docs/postgresql/17/functions-aggregate) — упорядоченные агрегаты.
- Cathy Tanimura, *SQL for Data Analysis* (O'Reilly, 2021) — глава 3 целиком про оконные функции в аналитике.
- Itzik Ben-Gan, *T-SQL Window Functions* (2-е изд., 2019) — синтаксис от Microsoft, но объяснение рамок окна и «островов и промежутков» лучшее из существующих.
- Peter Bruce, Andrew Bruce, Peter Gedeck, *Practical Statistics for Data Scientists* (2-е изд., 2020) — глава 1 про описательную статистику. На русском «Практическая статистика для специалистов Data Science».
- [Use The Index, Luke: Window Functions](https://use-the-index-luke.com/sql/partial-results/window-functions) — как оконные функции выполняются и почему бывают медленными.
