# Проект спринта 3. Оператор связи «Мегасеть»

## Постановка от заказчика

Коммерческий директор федерального оператора связи:

> «У нас три тарифа, и я не понимаю, какой из них нам выгоднее. Продуктовая команда хочет поднять цену на «Старте», финансы против. Ещё есть ощущение, что люди сидят не на своём тарифе — переплачивают или наоборот. И отдельно: у нас растёт отток, но откуда он растёт — непонятно. Разберись.»

Три задачи в одном абзаце, и ни одна не сформулирована так, чтобы на неё можно было ответить запросом. Как всегда, первый шаг — декомпозиция.

## Данные

Схема `telecom`. Поднять:

```bash
make telecom
```

| Таблица | Строк | Зернистость |
|---|---|---|
| `cities` | 12 | город |
| `tariffs` | 3 | тариф |
| `clients` | 2 400 | абонент |
| `calls` | ~342 000 | звонок |
| `messages` | ~167 000 | сообщение |
| `internet` | ~603 000 | интернет-сессия |
| `tickets` | 899 | обращение в поддержку |

Период: январь — июнь 2026. Часть абонентов подключилась до начала периода.

### Как устроена тарификация

Абонент платит фиксированную абонплату (`monthly_fee`), в которую входит пакет: минуты, SMS и гигабайты. Всё, что сверх пакета, тарифицируется поштучно по ценам `price_per_minute`, `price_per_sms`, `price_per_gb`.

Три правила, без которых расчёт будет неверным:

1. **Пакет обновляется каждый календарный месяц.** Неизрасходованное не переносится.
2. **Минуты округляются вверх поминутно, каждый звонок отдельно.** Звонок 1,2 минуты — это 2 минуты. Не суммируй сначала, а потом округляй: получится другая цифра, и она будет меньше настоящей.
3. **Гигабайты округляются вверх один раз за месяц**, по суммарному трафику. 1 ГБ = 1024 МБ.

### Что стоит знать заранее

- `clients.churn_date IS NULL` — абонент действующий.
- `clients.city_id` заполнен не у всех.
- `calls.duration_min = 0` — недозвон, разговора не было.
- В данных есть дефекты. Часть из них влияет на выручку.

## Что сделать

**Блок 1. Разведка схемы.**
1. Построй ER-диаграмму (можно текстом или схемой — как удобно) и опиши связи.
2. Размеры таблиц, границы периода, доля пропусков.
3. Проверь уникальность ключей: нет ли повторов там, где их быть не должно.

**Блок 2. Качество данных.**
4. Найди дубликаты в звонках. Реши, что считать дубликатом, и обоснуй.
5. Найди звонки, случившиеся после даты расторжения договора. Сколько их, на какую сумму влияют.
6. Разберись со звонками нулевой длительности: считать их звонками или нет, и как это меняет метрики.
7. Абоненты без города — сколько, что с ними делать в разрезах по городам.

**Блок 3. Абоненты.**
8. Распределение абонентов по тарифам, городам, регионам, типу (физлицо/юрлицо).
9. Динамика подключений и расторжений по месяцам.
10. Сколько абонентов действующих на конец периода.

**Блок 4. Потребление.**
11. Среднее и медианное потребление минут, SMS и гигабайт на абонента в месяц — в разрезе тарифов.
12. Какая доля абонентов выходит за пакет по каждому ресурсу.
13. Распределение звонков по часам суток и дням недели.

**Блок 5. Деньги.**
14. Посчитай ежемесячный счёт каждого абонента: абонплата плюс превышения. Это ядро проекта.
15. Средняя выручка на абонента (ARPU) по тарифам и по месяцам.
16. Какой тариф приносит больше выручки в сумме и на абонента.
17. Сколько абонентов платят больше, чем платили бы на другом тарифе. Для каждого такого — какой тариф был бы выгоднее и сколько бы он сэкономил.

**Блок 6. Отток.**
18. Уровень оттока по месяцам, тарифам, городам.
19. Отличаются ли ушедшие от оставшихся: по потреблению, по счёту, по числу обращений в поддержку, по сроку жизни.
20. Есть ли связь между обращениями в поддержку и последующим уходом.

**Блок 7. Ответ заказчику.**
21. Три вопроса директора, три ответа. По каждому — цифра, обоснование и рекомендация. Если на какой-то вопрос данных не хватает — сказать это прямо и объяснить, чего не хватает.

## Что сдать

1. `solution.sql` — запросы, пронумерованные по блокам, с вопросом в комментарии перед каждым.
2. `README.md` — отчёт для директора: три ответа сверху, обоснования ниже.
3. Список дефектов данных с оценкой влияния в деньгах.

## Критерии приёмки

Обязательные:

- [ ] ER-диаграмма или её текстовое описание есть.
- [ ] Определения зафиксированы до расчётов: что считаем активным абонентом, оттоком, месяцем.
- [ ] Найдены минимум 3 дефекта данных, по каждому — влияние на выручку и решение.
- [ ] Проверка на fan-out проведена явно: где-то в коде видно сравнение числа строк до и после соединения.
- [ ] Абоненты без города не потеряны молча.
- [ ] Минуты округляются поминутно, каждый звонок отдельно. Гигабайты — раз в месяц.
- [ ] Пакет считается по календарным месяцам, неизрасходованное не переносится.
- [ ] Логика счёта разложена на CTE с осмысленными именами.
- [ ] Есть санити-чек: сумма выручки по тарифам сходится с общей.
- [ ] Ряды по месяцам построены без дыр — месяц без данных виден как ноль, а не отсутствует.
- [ ] Пункт 17 (кто на неправильном тарифе) посчитан для каждого абонента, а не оценочно.
- [ ] Отчёт отвечает на три вопроса директора первым экраном.

Желательные:

- [ ] `DISTINCT ON` использован там, где он уместнее оконной функции.
- [ ] Есть оценка эффекта в деньгах хотя бы для одной рекомендации.
- [ ] Найден дефект, о котором в ТЗ не сказано.

## Подсказка по главной ловушке

Блок 5 — самая сложная часть, и там легко получить правдоподобную, но неверную цифру. Проверь себя так: возьми одного конкретного абонента, посчитай его счёт за один конкретный месяц руками, по определению тарифа, и сравни с тем, что даёт запрос. Расхождение найдётся почти наверняка, и это нормально — на то и проверка.
