# Спринт 18. PySpark

**1 неделя.** ClickHouse из спринта 17 решает задачу «быстро посчитать по тому, что уже лежит в базе». Этот спринт — про то, что происходит **до** базы: как сырые файлы из хранилища превращаются в строки витрины.

**Главная мысль:** Spark — не «pandas для больших данных». Это принципиально другая модель: ты не выполняешь операции, ты **строишь план**, а он выполняется целиком в момент, когда ты попросишь результат. Почти все ошибки новичка растут из непонимания этой разницы.

**На выходе:** пайплайн, который читает два миллиона грязных событий из объектного хранилища, чистит их, обогащает справочниками, агрегирует и кладёт в ClickHouse — и переживает повторный запуск.

Тренажёр: [trenazher/zadachi.py](trenazher/zadachi.py), 18 задач. Проверка — `make test SPRINT=18`.

Тренажёр на чистом Python: ни Spark, ни Java для него не нужны. Всё, на чём в Spark ошибаются, — не синтаксис, а модель исполнения, и её можно разобрать без JVM.

## Часть 1. Зачем распределённые вычисления

### 1.1. Когда pandas перестаёт работать

pandas держит данные в памяти одного процесса. Граница — не «миллион строк», а объём памяти минус то, что нужно на промежуточные результаты. Практически: датафрейм в гигабайт требует три-четыре гигабайта свободной памяти, потому что почти каждая операция создаёт копию.

Дальше три пути:

1. **Считать в базе.** Отправить агрегацию в PostgreSQL или ClickHouse. Правильный ответ в большинстве случаев, и модуль 6 начался именно с него.
2. **Считать порциями.** `chunksize` в pandas, ручное разбиение. Работает, пока задача разбивается.
3. **Распределить.** Spark. Нужен, когда данные не помещаются на одну машину или лежат в хранилище файлами, а не в базе.

**Честно про третий путь: он нужен реже, чем кажется.** Восемь миллионов строк из спринта 16 прекрасно живут в PostgreSQL. Spark начинается там, где данных десятки терабайт или где они изначально лежат в озере файлами — как в проекте этого спринта.

### 1.2. Архитектура

| Компонент | Что делает |
|---|---|
| **Driver** | держит план, разбивает работу на задачи, собирает результат |
| **Executor** | выполняет задачи над своей частью данных |
| **Cluster manager** | раздаёт ресурсы (YARN, Kubernetes, standalone) |

В режиме `local[*]` driver и executor'ы — потоки одного процесса. Кластер не нужен: всё, что мы делаем в этом спринте, работает на ноутбуке.

**Что из архитектуры важно для аналитика.** Driver — узкое место и единственная точка, где данные собираются вместе. Всё, что тянет данные на driver (`collect`, `toPandas`, `show` с большим числом строк), упирается в его память. Это [задача 17 тренажёра](trenazher/zadachi.py) и первая причина падений у новичков.

### 1.3. Ленивость: центральная идея

**Трансформация ничего не делает.** Она дописывает шаг в план. Ни одна строка не прочитана, пока не вызвано действие. [Задача 1](trenazher/zadachi.py).

```python
df = spark.read.json("s3a://raw/events/")   # ничего не прочитано
df = df.filter(df.event == "purchase")      # ничего не отфильтровано
df = df.withColumn("x", df.revenue * 2)     # ничего не посчитано
df.count()                                  # вот теперь всё выполнилось
```

Следствие, которое сбивает всех, кто пришёл из pandas: **ошибка обнаруживается не там, где написана.** Опечатка в имени столбца на строке 12 всплывёт на строке 40, на `show()`, и трассировка будет указывать туда.

Второе следствие полезнее: план оптимизируется целиком. Catalyst видит, что дальше стоит фильтр, и проталкивает его к чтению — файлы читаются уже отфильтрованными. В pandas такое невозможно в принципе.

### 1.4. Стадии и shuffle

**Shuffle** — перераспределение данных между партициями по сети, с записью на диск. Самая дорогая операция в Spark.

- **Узкая** трансформация (`filter`, `withColumn`, `select`) обрабатывает партицию независимо. Данные никуда не едут.
- **Широкая** (`groupBy`, `join`, `distinct`, `orderBy`) требует собрать вместе строки с одинаковым ключом — а они в разных партициях на разных машинах.

Каждая широкая трансформация закрывает **стадию**. Стадий на одну больше, чем shuffle-ов. [Задачи 2, 3, 4](trenazher/zadachi.py).

Число стадий видно в Spark UI, и по нему сразу понятно, во что обойдётся запрос: четыре стадии — это три записи промежуточных данных на диск.

**Почти всё искусство оптимизации Spark сводится к тому, чтобы shuffle-ов было меньше.**

## Часть 2. Хранилище и форматы

### 2.1. Объектное хранилище

S3 и совместимые с ним (MinIO, GCS, Azure Blob) — не файловая система, хотя выглядит похоже. Отличия, которые кусаются:

- **нет настоящих папок.** `dt=2026-06-01/` — часть имени объекта, а не каталог;
- **переименование — это копирование.** Дорого, и на этом ломаются наивные схемы записи «во временную папку, потом переименовать»;
- **список объектов — запрос по сети.** Тысячи мелких файлов упираются не в объём, а в число запросов метаданных;
- **согласованность.** Современный S3 строго согласован, но в older-совместимых хранилищах бывают сюрпризы.

### 2.2. Форматы

| Формат | Колоночный | Схема | Сжатие | Когда |
|---|---|---|---|---|
| CSV | нет | нет | внешнее | обмен с людьми, мелкие плоские файлы |
| JSON | нет | нет | внешнее | сырьё из трекинга, вложенные структуры |
| **Parquet** | **да** | **внутри** | **да** | **стандарт аналитики** |
| ORC | да | внутри | да | то же, чаще в экосистеме Hive |

[Задача 7](trenazher/zadachi.py).

**Parquet решает три проблемы разом.** Колоночный — читаются только нужные столбцы. Сжатый — меньше байт с диска и по сети. И **несёт схему внутри себя** — то есть снимает проблему из части 3.

Практическое правило пайплайна: сырьё приходит как приходит (JSON, CSV), а всё, что ты записываешь сам, — Parquet.

### 2.3. Партиционирование файлов

`s3a://lake/mart/dt=2026-06-01/part-0000.parquet` — вложенные «папки» с именами вида `столбец=значение`. Spark читает имена и **отсекает ненужные, не открывая файлы**. [Задача 8](trenazher/zadachi.py).

Работает только при фильтре по столбцу партиционирования и только если столбцов немного: число партиций — произведение кардинальностей.

Пример из задачи: партиционирование по дню и стране на 8 млн событий даёт 3 240 партиций по 0,14 МБ. Это **проблема мелких файлов** — на каждый нужен запрос метаданных, и чтение упирается в них. Ориентир — от сотни мегабайт на файл. [Задача 16](trenazher/zadachi.py).

**Ловушка, которая обязательно встретится в проекте.** `partitionBy("dt")` кладёт файлы в папки `dt=...` и **удаляет `dt` из самих файлов**. Spark потом восстановит его из пути, а вот ClickHouse, читая тот же Parquet через `s3()`, столбца не увидит — и запрос упадёт. Достаётся он из виртуального столбца `_path` регуляркой.

## Часть 3. Схема

### 3.1. Почему `inferSchema` не используют в проде

Spark читает часть файла и выводит типы по ней. Три способа, которыми это ломается, — [задача 6](trenazher/zadachi.py):

| Что в данных | Что выведет | Что сломается |
|---|---|---|
| `"001"`, `"002"` | `IntegerType` | ведущие нули потеряны, идентификатор превратился в число |
| `"1.50"`, `"2.25"` | `DoubleType` | деньги во Float, копейки поплыли |
| `"1"`, `"2"`, `"abc"` | зависит от выборки | завтра приедет файл без букв — тип сменится |

Третья строка — худшая. Пайплайн не падает, он начинает считать не то, и обнаруживается это через месяц.

Плюс `inferSchema` требует **лишнего прохода по данным** — на терабайте это ощутимо.

**Схема задаётся явно**, через `StructType`. [Задача 5](trenazher/zadachi.py). Это первый пункт критериев приёмки проекта.

### 3.2. Битые строки

Режим `PERMISSIVE` с `columnNameOfCorruptRecord` кладёт неразобранные строки в отдельный столбец вместо того, чтобы падать. Альтернативы: `DROPMALFORMED` (молча выбросить — почти всегда плохо) и `FAILFAST` (упасть на первой).

**Ограничение, на которое ты наткнёшься.** Запрос, ссылающийся **только** на `_corrupt_record`, Spark запрещает:

```
AnalysisException: Since Spark 2.3, the queries from raw JSON/CSV files are
disallowed when the referenced columns only include the internal corrupt
record column
```

И добавить в запрос настоящий столбец не помогает: Catalyst выбросит его, если тот не влияет на результат.

Правильное решение — не обходить ограничение, а **записать разобранное в staging-слой Parquet и считать статистику оттуда**. Заодно перестаёшь перечитывать и переразбирать JSON на каждом действии. Это ровно те слои из спринта 16: raw → staging → mart. Ограничение Spark просто заставляет сделать то, что надо было сделать и так.

## Часть 4. Оптимизация

### 4.1. Broadcast join

Обычное соединение перемешивает **обе** стороны по ключу. Если одна из сторон — справочник на пару мегабайт, дешевле разослать его копию каждому исполнителю: тогда shuffle не нужен вовсе. [Задачи 9 и 13](trenazher/zadachi.py).

```python
enriched = events.join(F.broadcast(users), on="user_id", how="left")
```

**Самая результативная оптимизация в Spark**, и в аналитике она применима почти всегда: факт большой, измерения маленькие. Spark умеет включать её сам по `spark.sql.autoBroadcastJoinThreshold` (по умолчанию 10 МБ), но оценка размера бывает неверной — явный `broadcast()` надёжнее.

Обратная сторона: рассылка справочника на 500 МБ убьёт исполнителей по памяти.

### 4.2. Партиции

[Задача 10](trenazher/zadachi.py).

- **`repartition(n)`** перемешивает и раскладывает ровно. Это shuffle.
- **`coalesce(n)`** склеивает соседние партиции без перемешивания. Дёшево, но перекос останется и даже усилится.

Увеличить число партиций через `coalesce` нельзя — только `repartition`.

Сколько брать: столько, чтобы задач хватило на все ядра, но каждая обрабатывала осмысленный объём. Ориентир — от полумиллиона до нескольких миллионов строк на партицию.

Отдельно про `spark.sql.shuffle.partitions`: **по умолчанию 200**, и это значение из мира кластеров. Для двух миллионов строк на ноутбуке это двести задач по десять тысяч строк, и накладные расходы съедают всю выгоду.

### 4.3. Перекос

199 партиций из 200 отработали, одна висит час. [Задача 11](trenazher/zadachi.py).

Причина почти всегда одна: доминирующее значение ключа. NULL, `unknown`, гостевой пользователь, на которого списаны все анонимные события. Соединение по такому ключу собирает половину данных в одну партицию.

Лечится: отделить проблемный ключ и обработать отдельно; добавить к ключу случайный суффикс (salting); включить adaptive query execution, который умеет разбивать перекошенные партиции сам.

### 4.4. Кэш

`cache()` — не бесплатная оптимизация, а размен памяти на вычисления. [Задача 12](trenazher/zadachi.py).

Вредит, когда: датафрейм используется один раз (чистая трата), не помещается в память (вытесняет сам себя, и пересчёт идёт всё равно), или пересчитывается дёшево.

Помогает, когда датафрейм дорого получен и используется несколько раз — например, когда с него считают и статистику, и витрину.

Альтернатива кэшу, которая часто лучше: **записать промежуточный результат в Parquet**. Он переживёт падение задачи, его можно посмотреть, и он не съедает память.

### 4.5. Catalyst

Оптимизатор, который переписывает план: проталкивает фильтры к чтению, выбрасывает неиспользуемые столбцы, переставляет соединения.

Практические следствия:

- **не оптимизируй руками то, что он сделает сам.** Порядок `filter` и `select` в коде не важен;
- **но он не может протолкнуть то, чего не понимает.** Фильтр внутри Python UDF для него чёрный ящик, и данные будут прочитаны целиком;
- **`explain()` показывает итоговый план.** Читать его — единственный способ узнать, что происходит на самом деле.

Отсюда правило: **UDF на Python — последнее средство.** Каждая строка гоняется между JVM и Python, оптимизатор слепнет. Почти всё, что хочется написать UDF, есть во встроенных функциях `pyspark.sql.functions`.

## Часть 5. Запись и идемпотентность

### 5.1. Режимы

[Задача 14](trenazher/zadachi.py).

| Режим | Что делает |
|---|---|
| `append` | дописывает |
| `overwrite` | перезаписывает |
| `errorifexists` | падает, если данные есть |
| `ignore` | ничего не делает, если данные есть |

**`append` не идемпотентен.** Повторный запуск задвоит данные, а повторные запуски случаются всегда: ретрай упавшей задачи, ручной запуск «на всякий случай», перекрытие окон загрузки из спринта 16.

### 5.2. Динамическая перезапись партиций

Ключевая настройка, и она не по умолчанию:

```python
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")
```

Без неё `overwrite` с `partitionBy` сносит **всю таблицу**, а не только пересчитываемые партиции. [Задачи 15 и 18](trenazher/zadachi.py).

Три сценария повторного запуска:

| Режим | Задвоится | Потеряется |
|---|---|---|
| `append` | партиции, попавшие в оба набора | ничего |
| `overwrite` + dynamic | ничего | ничего |
| `overwrite` + static | ничего | **партиции, которых нет в новых данных** |

Третий — тихая потеря истории, которую замечают через неделю. Оба `overwrite` идемпотентны, но у статического цена — вся история.

**Рабочий рецепт: `overwrite` + `partitionBy` + dynamic.** Пересчитываешь день — перезаписывается только он.

### 5.3. Что тянуть на driver

[Задача 17](trenazher/zadachi.py). Две поправки к наивному расчёту «влезет или нет»:

- **строка в памяти Python занимает в разы больше**, чем в Parquet;
- **миллионы строк на driver не тянут независимо от размера** — он не для этого.

`collect()` на большом датафрейме — самая частая причина падения задачи у новичка. Второе место — `toPandas()`, который делает то же самое, но выглядит невиннее: он держит и JVM-, и Python-копию.

Что вместо: `write` (результат в хранилище), `take(n)` и `show(n)` (посмотреть глазами), агрегация до сотен строк — и только потом `collect`.

## Часть 6. Spark SQL и практика

### 6.1. SQL или DataFrame API

```python
df.createOrReplaceTempView("events")
spark.sql("SELECT device, count(*) FROM events GROUP BY device")
```

**Разницы в производительности нет** — оба идут через Catalyst и дают один план. Выбор по читаемости:

- **SQL** — когда логика выражается запросом: агрегации, соединения, оконные функции. Плюс её понимают все, включая тех, кто Spark не знает.
- **DataFrame API** — когда нужна параметризация, переиспользуемые куски, цикл по столбцам, тесты.

Смешивать нормально. В пайплайне обычно: чтение и очистка на API, бизнес-логика на SQL.

### 6.2. Spark UI

`localhost:4040` во время работы задачи. Что смотреть:

- **Jobs** — сколько стадий, где время;
- **Stages** — распределение времени по задачам. Одна задача в десять раз дольше остальных — перекос;
- **SQL** — план запроса с реальными числами строк на каждом узле;
- **Storage** — что закэшировано и сколько занимает.

Пункт **Stages** — тот же навык, что чтение `EXPLAIN ANALYZE` в спринте 16, только в браузере.

### 6.3. Локальный запуск: что нужно знать заранее

Из опыта сборки этого спринта — три вещи, которые стоят потерянного вечера:

1. **Первый `spark-submit` с `--packages` качает jar-ы с Maven.** `hadoop-aws` и AWS SDK — это 275 МБ. Один раз это заняло четырнадцать минут. Дальше они в кэше.
2. **Памяти в Docker обычно мало.** `--driver-memory 3g` при лимите 3,8 ГБ на весь Docker убивает контейнер по OOM с кодом 137, без внятного сообщения.
3. **`local[*]` — это не «медленный кластер»**, а полноценный Spark. Всё, кроме сетевого shuffle между машинами, работает так же.

## Что должно остаться в голове

- Трансформация ничего не делает. Выполняется всё разом, на действии.
- Ошибка обнаруживается не там, где написана.
- Стадий на одну больше, чем shuffle-ов. Меньше shuffle — быстрее задача.
- `inferSchema` не используют в проде: ведущие нули, деньги во Float, тип, зависящий от выборки.
- `_corrupt_record` нельзя запросить в одиночку — это повод завести staging-слой, а не обходной приём.
- Parquet для всего, что записываешь сам. Сырьё — как приходит.
- `partitionBy` пишет столбец в путь, а не в файл. Читателю не-Spark придётся доставать его из пути.
- Broadcast маленькой стороны убирает shuffle целиком.
- `coalesce` не перемешивает и оставляет перекос; `repartition` перемешивает и выравнивает.
- `spark.sql.shuffle.partitions` по умолчанию 200 — это значение для кластера, не для ноутбука.
- Кэш вредит, когда датафрейм используется один раз или не влезает в память. Часто лучше записать Parquet.
- UDF на Python ослепляет оптимизатор. Сначала ищи встроенную функцию.
- `append` не идемпотентен. `overwrite` без dynamic сносит всю таблицу.
- `collect` и `toPandas` — про driver, а не про данные.

- [Spark SQL Performance Tuning](https://spark.apache.org/docs/latest/sql-performance-tuning.html) — короткая страница про broadcast, партиции и adaptive query execution. Прочитать целиком.
- [Web UI](https://spark.apache.org/docs/latest/web-ui.html) — что где смотреть в интерфейсе.

**Книги**

- Jules Damji и др., *Learning Spark*, 2-е изд. (O'Reilly, 2020) — [бесплатный PDF у Databricks](https://pages.databricks.com/rs/094-YMS-629/images/LearningSpark2.0.pdf). Лучшая точка входа. Главы 3–5 закрывают DataFrame API и Spark SQL, глава 7 — оптимизацию.
- Holden Karau, Rachel Warren, *High Performance Spark*, 2-е изд. (2023) — про shuffle, перекос и то, что происходит под капотом. Читать после того, как первый пайплайн заработал.
- Bill Chambers, Matei Zaharia, [*Spark: The Definitive Guide*](https://www.oreilly.com/library/view/spark-the-definitive/9781491912201/) — самый полный справочник. Толстый, читается выборочно.
