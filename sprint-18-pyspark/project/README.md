# Проект спринта 18. Пайплайн S3 → PySpark → ClickHouse

**С ревью.** Сдаёшь в `solutions/`, я проверяю по критериям приёмки.

---

## Постановка

Трекинг «Потока+» пишет сырые события в объектное хранилище: по файлу на день, JSON Lines, gzip. Никто их не читал — аналитика жила на выгрузках из продовой базы, и продакт наконец спросил то, чего в выгрузке нет.

Файлы грязные. Они всегда грязные: трекер ретраит доставку, часть строк обрывается на середине, поля приходят то числом, то строкой, события опаздывают на несколько дней.

**Задача:** построить пайплайн, который превращает это в витрину, пригодную для дашборда, и делает это так, чтобы его можно было запустить повторно и не испортить данные.

## Окружение

```bash
make s3       # MinIO + генерация логов + заливка (~50 МБ, около двух минут)
make spark    # поднять Spark
```

| Что | Где |
|---|---|
| S3 API (MinIO) | `localhost:9002`, изнутри контейнеров `http://minio:9000` |
| Консоль MinIO | `localhost:9001`, `analyst` / `analyst123` |
| Бакеты | `raw` — сырьё, `lake` — то, что делаешь ты |
| ClickHouse | `make ch-up`, база `course` |

Запуск скрипта:

```bash
make spark-sh CMD='spark-submit --master local[*] --driver-memory 1600m \
  --packages $(cat /course/sprint-18-pyspark/project/pipeline/packages.txt) \
  /course/sprint-18-pyspark/project/pipeline/твой_скрипт.py'
```

В [`pipeline/common.py`](pipeline/common.py) уже лежит `get_spark()` — сессия, настроенная на MinIO. Импортируй оттуда, не копируй конфиг в каждый скрипт.

**Три вещи про окружение, которые сэкономят тебе вечер.**

1. **Первый запуск качает 275 МБ jar-ов** (`hadoop-aws` и AWS SDK) с Maven. У меня это заняло четырнадцать минут. Дальше они лежат в кэше на томе, и запуск идёт секунды. Не думай, что всё зависло.
2. **Памяти в Docker мало.** У меня на всё 3,8 ГБ, из них ClickHouse и MinIO уже съели полгигабайта. `--driver-memory 3g` убивает контейнер по OOM (код 137). Рабочее значение — `1600m`. Если у тебя Docker Desktop настроен щедрее, бери больше.
3. **`spark.sql.shuffle.partitions` по умолчанию 200.** Для двух миллионов строк на ноутбуке это двести задач по десять тысяч строк, и накладные расходы съедают всю выгоду. В `get_spark()` стоит 8 — поменяй, если поймёшь, что нужно иначе, но осознанно.

## Что сдать

### 1. Пайплайн

`pipeline/*.py` — скрипты, запускаемые через `spark-submit`. Шаги:

**Чтение.** Схема задана **явно**, через `StructType`. `inferSchema` в этом проекте запрещён, и не из вредности: он читает часть файла и выводит типы по ней, а завтра приедет файл, где в столбце появится буква.

**Очистка.** Битые строки отделить, дубли снять, типы привести, регистр нормализовать, пропуски заменить явными значениями.

**Окно.** Определи, за какой период считаешь витрину, и что делаешь с событиями вне окна. Решение обоснуй: выбросить, положить в отдельное место или пересчитать соседнюю партицию — три разных ответа, все защитимые.

**Обогащение.** Соединение со справочниками. Справочники маленькие — используй это.

**Агрегация.** Витрина: день × устройство × тариф, с числом событий, уникальных пользователей, покупок и выручкой.

**Запись.** Parquet в `s3a://lake/`, партиционированно.

**Загрузка в ClickHouse.** Таблица `course.mart_daily`.

### 2. Разбор плана выполнения

`plan.md`:

- где в пайплайне происходит **shuffle** и почему он неизбежен (или как ты его убрал);
- сколько получилось стадий;
- какая стратегия выбрана для каждого соединения — покажи `explain()`;
- где ты поставил `cache()` и почему, или почему нигде.

Инструменты для рассуждения — в [тренажёре](../trenazher/zadachi.py): `find_shuffles`, `count_stages`, `broadcast_decision`, `cache_decision`.

### 3. Доказательство идемпотентности

`idempotent.md`. Запусти пайплайн дважды и покажи, что числа не изменились. Не «должно быть идемпотентно», а два прогона и таблица сравнения.

Отдельно объясни, **какой режим записи** ты выбрал и что произойдёт с партициями, которых нет в новых данных.

### 4. Отчёт о качестве данных

`quality.md` — сколько строк на каждом шаге и сколько потерялось. Читается как воронка: прочитано → не битых → без дублей → в окне → обогащено → в витрине.

Это не бюрократия. Пайплайн без такого отчёта однажды начнёт терять четверть данных, и никто не заметит.

## Три ловушки, которые ты обязательно встретишь

**1. `_corrupt_record` нельзя запросить в одиночку.**

```
AnalysisException: Since Spark 2.3, the queries from raw JSON/CSV files are
disallowed when the referenced columns only include the internal corrupt
record column
```

Запрос вроде «посчитай, сколько битых строк» падает, даже если ты добавил в него настоящий столбец: Catalyst выбросит его, если тот не влияет на результат.

Обходить это добавлением фиктивных столбцов — плохое решение. Правильное — **записать разобранное в staging-слой Parquet и считать статистику оттуда**. Заодно перестанешь перечитывать и переразбирать JSON на каждом действии.

Это и есть слои из спринта 16: raw → staging → mart. Ограничение Spark просто заставляет тебя сделать то, что надо было сделать и так.

**2. Дата в имени папки не равна дате события.**

В партиции `dt=2026-06-15` лежат 840 событий, произошедших раньше. Взять дату из имени папки — быстро и неверно. Взять из `ts` — верно, но тогда запись породит партиции, которых ты не ждал, включая события из будущего.

**3. `partitionBy` пишет столбец в путь, а не в файл.**

Spark, записывая с `partitionBy("dt")`, кладёт файлы в папки `dt=2026-06-01/` и **удаляет `dt` из самих файлов**. ClickHouse, читая их через `s3()`, столбца `dt` не увидит — и запрос упадёт с `UNKNOWN_IDENTIFIER`.

Достаётся он из виртуального столбца `_path`:

```sql
toDate(extract(_path, 'dt=(\\d{4}-\\d{2}-\\d{2})')) AS dt
```

Тот же фокус нужен всем, кто читает партиционированный Parquet не Spark-ом.

## Критерии приёмки

**Обязательное**

- [ ] Схема датафрейма задана явно через `StructType`, `inferSchema` не используется.
- [ ] Битые строки обработаны режимом `PERMISSIVE` с `_corrupt_record`, их число посчитано.
- [ ] Дубли сняты по ключу события, число удалённых посчитано.
- [ ] `revenue` разобран во всех трёх видах, включая строку с валютой.
- [ ] `user_id` приведён к числу до соединения со справочником.
- [ ] `device` нормализован, `country` и `utm_source` не теряются на NULL.
- [ ] Окно расчёта определено явно; решение по событиям вне окна принято и обосновано.
- [ ] Соединение со справочником — **broadcast**, и это видно в `explain()`.
- [ ] `collect()` и `toPandas()` не вызываются на больших датафреймах.
- [ ] Партиционирование при записи осмысленно; названо, сколько получилось файлов и какого размера.
- [ ] Пайплайн идемпотентен, и это **показано двумя прогонами**, а не заявлено.
- [ ] Названо, что произойдёт с партициями, которых нет в новых данных.
- [ ] Витрина загружена в ClickHouse, числа сходятся с тем, что посчитал Spark.
- [ ] Отчёт о качестве: сколько строк на каждом шаге.
- [ ] Разобрано, где происходит shuffle и почему.
- [ ] Числа совпадают с эталонными, либо расхождение объяснено.

**Желательное**

- [ ] Staging-слой в Parquet отделён от витрины.
- [ ] Второй справочник (`products`) подключён, витрина по категориям.
- [ ] Посмотрел Spark UI и приложил число стадий и время самой долгой.
- [ ] Проверил, что будет при `spark.sql.shuffle.partitions = 200`, и замерил разницу.
- [ ] Тесты на данные для витрины — по образцу первой части тренажёра спринта 15.
- [ ] Обработка опоздавших событий не выбрасыванием, а пересчётом затронутых партиций.
